# ЛК БНП: рабочий контекст интеграции

Снято 09.10.2026 с трёх файлов заказчика. Это контракт, с которым собирается пакет на исполнительную надпись. Промышленного HTTP API в этих файлах нет.

Источники:

- `Информация по Интеграции/json описание полей..docx` — файл манифеста заявления;
- `Информация по Интеграции/Справочники БНП.docx` — услуги, типы задолженности, типы документов;
- `Информация по Интеграции/Инструкция по работе с ЛК для совершения ИН удаленно.pdf` — сценарий личного кабинета на https://enotariat.by (10 страниц).

Куда это ложится в ТЗ: группа 3, модули 4.2.3 и 4.2.4 (пакет нотариусу, ЭЦП, загрузка надписи или отказа), интеграция 4.2.10.5. Сводка процесса — `docs/tz/PM_ZADOLZHENNOST.md`, разделы 8 и 14. Код проверки манифеста уже есть и в личный кабинет ничего не отправляет.

## Что уже есть в коде

Шлюз: `app/gateway/app/integrations/bnp/`.

- `schemas.py` — `BnpManifest`: UTF-8, условная обязательность по типу лица, личный номер, УНП, сумма `10.00`, даты `YYYY-MM-DD`, `serviceId` / `typeId` / `docType` по справочникам.
- `bnp_dictionaries.json` и фикстура `app/backend/apps/nsi/fixtures/bnp_dictionaries.json` — те же три справочника. Пересборка: из каталога `app` команда `python scripts/extract_bnp_dictionaries.py`.
- `StubBnpClient.submit()` проверяет манифест и размеры файлов, пишет номер `stub-…`, в кабинет не ходит. Замена — наследник `BnpClient`. Карточка дела: `POST /api/v1/claims/{id}/send-notary/` ставит `submission_mode=stub`.

В справочнике 39 услуг (из них 32 — `exec_order`), 108 типов задолженности, 10 типов документов. Коды задолженности, на которые ссылаются услуги, в справочнике типов есть.

## Как устроен обмен

Документы описывают файл манифеста и ручную работу в кабинете. Поля получателя, статуса и результата в JSON нет: их выбирают и читают в интерфейсе.

ТЗ 4.2.10.5: промышленного API нет; допустим фоновый робот по учётным данным заказчика, если интерфейс это позволяет. При изменении кабинета — резервный обмен по согласованию. Способ (файл манифеста, робот, ручная выгрузка) в этих трёх документах не выбран.

Сценарий кабинета:

1. Представитель юридического лица лично подаёт нотариусу заявление о создании кабинета. Нужны документ, удостоверяющий личность, и доверенность (бумага или электронный документ). ЭЦП для создания кабинета не нужна. Нотариус выдаёт логин и секретный код восстановления; пароль приходит SMS и на e-mail.
2. Вход: https://enotariat.by → «Войти» → логин, пароль, код подтверждения из SMS или e-mail.
3. Раздел «Нотариальные действия» → блок «Исполнительная надпись» → «Создать» → вид надписи по пункту перечня (постановление Совета Министров от 13.06.2024 № 418).
4. Сведения о должнике и солидарных должниках (обязательные поля помечены «*»), затем о задолженности.
5. Вложения: тип документа и файл. На портал принимаются только `.pdf` не больше 15 МБ.
6. Получатель: «Нотариус РБ» (любой нотариус страны) либо нотариальный округ (пример в инструкции — Витебский).
7. Контакты заявителя и сообщение нотариусу. После каждого блока — «Сохранить». Когда обязательные поля и документы на месте, появляется «Отправить».
8. Статус смотрят в том же блоке «Исполнительная надпись».
9. Готовая надпись: запись со статусом «Завершено» → вкладка «Документы нотариуса» → скачать электронный документ. Надпись, подписанная нотариусом ЭЦП в период действия сертификата, сохраняет силу после отзыва открытого ключа.

В инструкции назван только статус «Завершено». Каталога статусов, метода опроса и отдельного шага скачивания отказа нет. Типы документов `executive_inscription` и `rejection_order` в справочнике есть: это результат нотариуса, не исходящий пакет.

Контакты по электронному взаимодействию из инструкции: Шафранович Денис Николаевич, начальник отдела информационных технологий БНП, 8 (017) 325-50-52; Наплёха Анастасия Александровна, специалист отдела по разработке проектов нормативных правовых актов, 8 (017) 323-38-23.

## Манифест

Кодировка UTF-8. Корень: `version` (целое, обязательно) и `applications` (массив, обязательно). В одном файле может быть несколько заявлений.

| Поле | Тип | Когда обязательно | Ограничение |
|---|---|---|---|
| `externalId` | string | всегда | идентификатор заявления во внешней системе (ПМ) |
| `contactData` | string | всегда | контактные данные |
| `notificationE-mail` | string | всегда | e-mail; несколько через запятую. В имени ключа дефис |
| `userMessage` | string | всегда | сообщение нотариусу |
| `serviceId` | integer | всегда | из справочника услуг |
| `debtors[].personType` | string | всегда | `natural` / `legal` / `sole_trader` |
| `debtors[].personalId` | string | `natural`, `sole_trader` | до 14 символов, латинские прописные, проверка структуры |
| `debtors[].secondName` / `firstName` / `middleName` | string | `natural`, `sole_trader` | фамилия, имя, отчество |
| `debtors[].unp` | string | `legal`, `sole_trader` | до 9 символов, проверка структуры |
| `debtors[].regNumber` / `regName` | string | `legal` | регистрационный номер и наименование |
| `debts[].description` | string | если нет `typeId` | описание долга |
| `debts[].startDate` / `endDate` | string | если нет `dateAt` | `YYYY-MM-DD`, оба вместе |
| `debts[].dateAt` | string | если нет пары дат | `YYYY-MM-DD` |
| `debts[].amount` | string | всегда | точка и два знака, пример `10.00` |
| `debts[].currency` | string | всегда | буквенный код, пример `BYN` |
| `debts[].typeId` | string | из справочника; строка документа помечает поле как обязательное и одновременно разрешает описание вместо кода | код типа задолженности, допустимый для выбранной услуги |
| `docs[].fileName` | string | всегда | имя файла документа, `.pdf` |
| `docs[].signatureName` | string | всегда | имя файла ЭЦП в пакете: `.pdf.sgn` или `.pdf.p7s` |
| `docs[].docType` | string | всегда | из справочника типов документов |
| `docs[].detachedSign` | boolean | всегда | `true` — ЭЦП отдельным файлом |

В таблице исходника `typeId` стоит как обязательное, а `description` — как замена отсутствующего `typeId`. Валидатор шлюза принимает одно из двух. Отчество в исходнике обязательно для физического лица и ИП; послабления для лица без отчества документ не даёт.

Маска личного номера в docx не расписана, только «проверка структуры» и латинские прописные, максимум 14 символов. В коде это структура идентификационного номера РБ: 7 цифр, буква, 3 цифры, 2 буквы, цифра. УНП в коде — ровно 9 цифр.

## Подпись и состав пакета

Файлы `.pdf.sgn` и `.pdf.p7s` — это ЭЦП, которая идёт в пакете вместе с документом. В манифесте имя этого файла — `signatureName`. Тело документа — `fileName`, формат `.pdf`, не больше 15 МБ: так файлы принимает кабинет. `detachedSign: true` значит, что подпись лежит отдельным файлом, а не внутри PDF. Оба файла пакета не больше 15 МБ.

Каждый исходящий документ подписывает ЭЦП представителя юридического лица, который создал кабинет. Сертификат — республиканский удостоверяющий центр ГосСУОК. Доверенность на обращение за надписью подписывает ЭЦП руководителя.

Если в подписанном заявлении нет даты и исходящего номера, отдельно кладётся регистрационно-контрольная карточка (РКК) в PDF, подписанная заявителем, с типом «иной документ». Та же логика для номера доверенности, если локальные акты юридического лица этот реквизит требуют. В инструкции один раз опечатка «РРК».

Инструкция приводит перечень вложений как пример для пункта 7 перечня (кредитный договор, услуга `serviceId` 318), не как пакет ЖКУ:

1. заявление о совершении надписи удалённо, электронный документ, ЭЦП заявителя; образец лежит в кабинете, раздел «Образцы документов»;
2. расчёт суммы задолженности, неустойки (штрафа, пеней), ЭЦП уполномоченного на подписание расчёта;
3. доверенность на обращение за надписями, электронный документ, ЭЦП руководителя, с датой совершения;
4. документ о полномочиях подписывать расчёт — только если таких полномочий нет в доверенности; бумага (скан + ЭЦП заявителя) или электронный документ (ЭЦП руководителя);
5. кредитный договор или договор с существенными условиями кредитного: скан бумаги с ЭЦП заявителя, электронный документ либо его экранная форма с ЭЦП заявителя;
6. договор поручительства — тем же порядком;
7. документ об оплате нотариального тарифа. Его можно приложить после сообщения нотариуса о сумме и реквизитах.

Пакет ПМ по ТЗ 4.2.4.2 для ЖКУ другой по составу оснований: заявление из шаблона ПМ, расчёт из АИС (прикладывает пользователь), доверенность при необходимости, сканы договоров вручную. ПМ проверяет полноту чек-листа и не проверяет содержание. Переход «Направлено нотариусу» блокируется без даты вручения предупреждения или уведомления и без нотариального тарифа. Тариф считает АИС (постановление Совета Министров от 27.01.2026 № 46). Это не отменяет правило кабинета: квитанция об оплате может уйти вторым шагом, после сообщения нотариуса.

Типы исходящих и входящих документов:

| `docTypeId` | Название |
|---|---|
| `application` | Заявление |
| `debt_calculation` | Расчет задолженности |
| `proxy` | Доверенность |
| `agreement_contract` | Договор |
| `other_document` | Иной документ |
| `transfer_document` | Документ о передаче |
| `acknowledgment_document` | Документ, подтверждающий письменное признание |
| `payment_order` | Квитанция об оплате |
| `executive_inscription` | Исполнительная надпись |
| `rejection_order` | Постановление об отказе в совершении исполнительной надписи |

## Услуги, которые относятся к задолженности за ЖКУ

Вид надписи в кабинете выбирается по пункту перечня. Для долга за ЖКУ в справочнике три услуги `exec_order`. Какую из них ставит начисляющая организация, а какую поставщик, документы не фиксируют: пункт не выбирать догадкой.

`serviceId` **572**, пункт 9. Задолженность за поставленные через присоединённую сеть электрическую энергию, тепловую энергию, газ, воду.

| Код | Смысл |
|---|---|
| `dolg_9` | электроэнергия, тепло, газ и вода вместе |
| `dolg_9_1` | электрическая энергия |
| `dolg_9_2` | тепловая энергия |
| `dolg_9_3` | газ |
| `dolg_9_4` | вода |
| `dolg_28` | неустойка |
| `dolg_shtraf` | штраф |
| `dolg2_3` | пени |

`serviceId` **571**, пункт 21. Плата за жилищно-коммунальные услуги, пользование жилым помещением, управление общим имуществом, земельный налог или арендная плата за участки под жилыми домами. Коды — комбинации, не отдельные услуги: `dolg9`, `dolg9_3`, `dolg9_4`, `dolg9_5`, `dolg9_6`, `dolg9_7`, `dolg62`, `dolg_21`, `dolg_21_1` … `dolg_21_4`, `dolg_21_40` … `dolg_21_47`, плюс `dolg2_3` (пени).

`serviceId` **576**, пункт 22. Пересечение платы за ЖКУ, пользования жильём, управления и земельного налога: `dolg9`, `dolg9_6`, `dolg9_7`, `dolg_21`, `dolg_21_1` … `dolg_21_4`, `inoe`, `dolg2_3`.

Рядом, но это пример из инструкции, не пакет ЖКУ: `serviceId` **318**, пункт 7, кредитный договор (`dolg7`, `dolg7_1`, `dolg30`, `dolg31`, `dolg_proc`, `dolg_28`, `dolg_shtraf`, `inoe`, `dolg2_3`).

Коды `dolg9*` и `dolg_9*` — разные позиции справочника. Путать их нельзя.

Прочие `typeId` услуг, не надпись: `temp_actions`, `duplicate`, `postponement`, `postponement_exeс`. В последнем коде последняя буква — кириллическая «с» (U+0441), так в исходном docx. Не заменять на латинскую.

## Что не закрыто этими файлами

- Нет URL, авторизации и формата промышленного API. Есть файл манифеста и веб-кабинет.
- Нет поля нотариуса-получателя, номера обращения и статуса в JSON.
- Нет каталога статусов, кроме «Завершено», и нет описанного скачивания отказа. ТЗ требует грузить в ПМ и надпись, и постановление об отказе.
- Не назначен `serviceId` для начисляющей организации и для поставщика.
- Тариф в ТЗ обязателен до статуса «Направлено нотариусу» и считается в АИС. Квитанция в кабинете может уйти после сообщения нотариуса о сумме.
