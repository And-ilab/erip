# ЕРИП — ПМ «Модуль по работе с задолженностью»

Рабочий контур для эксплуатации. Функция внутри ПМ должна быть пригодна к работе. Внешний канал на заглушке задачей не закрыт: это названо в [STUBS.md](STUBS.md).

Состав приложения:

- **backend** — Django 5 + DRF: доменная модель, CRUD/REST, роли и контуры доступа, импорт выгрузок АИС «Расчет-ЖКУ», оповещения, журналы ошибок и аудита;
- **gateway** — FastAPI: асинхронная доставка оповещений (каналы на заглушках) и каркас интеграций ПРИС и БНП;
- **frontend** — Angular 18 + Angular Material;
- PostgreSQL 16, Redis, NGINX.

```
Angular ──/api/──> Django ──(httpx + X-Internal-Token)──> FastAPI ──> адаптеры каналов (заглушки)
                      ▲                                    │
                      └── callback статуса, ErrorLog       └──> ПРИС / БНП (заглушки)
```

`/gw/` снаружи без служебного токена отвечает 401. Браузер ходит только в `/api/`.

## Запуск в Docker

Один `docker compose up --build` из каталога `app` собирает три образа под текущий код. Nginx-образ сам ставит зависимости Angular и кладёт `dist/erip/browser`. Стили подключаются обычным файлом: отложенная вставка через `onload` не срабатывает из‑за `Content-Security-Policy` nginx, и без этого съезжают поля. Та же политика пускает worker карты и встроенный просмотр PDF с `blob:` (`worker-src`, `frame-src`, `object-src`). Подложка читается с этого же сервера, файл `maps/belarus.pmtiles`: образ nginx при сборке берёт срез Беларуси из последней суточной сборки Protomaps, которая ещё отвечает (`https://build.protomaps.com/ГГГГММДД.pmtiles`). Старая дата в адресе отдаёт 404: сборки хранятся недолго. Браузер за тайлами наружу не ходит. JSON, скрипты и стили nginx отдаёт со сжатием gzip. Ответ API до 1 МБ остаётся в памяти прокси и во временный файл не сбрасывается. Соединение с backend и шлюзом переиспользуется. Файлы `.js` и `.css` с хешем в имени кэшируются на 30 дней, `index.html` запрашивается заново. Подписи городов и улиц читают шрифт из `frontend/public/fonts`: сборка nginx копирует его в страницу. Локальный `runserver` отдаёт этот файл кусками по заголовку `Range`: иначе на каждый тайл ушёл бы весь архив. Шрифт иконок лежит в `ng-media`, потому что `/media/` отдаёт вложения Django, а не файлы Angular. Backend ставит шрифты DejaVu и Liberation Serif: PDF предупреждения и печатных форм пишется кириллицей, лист формы собирает WeasyPrint. CSV обзвона и вложения лежат в томе `media` и отдаются по `/media/`. PostgreSQL и Redis поднимаются рядом. Повторная сборка не стирает базу: при старте backend выполняет `migrate`.

```powershell
cd app
Copy-Item .env.example .env -ErrorAction SilentlyContinue
docker compose up --build
```

Первый запуск сам готовит базу: миграции Django, схема `gateway` и схема `ais` из `postgres/ais_3nf.sql` (все таблицы 3НФ). Отдельный `migrate` и `loaddata` после `up` не нужны. Скрипты в `docker-entrypoint-initdb.d` выполняются только на пустом томе `pgdata`. Если том уже был создан раньше, схему накатывают один раз:

```powershell
Get-Content .\postgres\ais_3nf.sql | docker compose exec -T postgres psql -U erip -d erip -v ON_ERROR_STOP=1
```

Пример `.env` поднимает локальный контур с `DJANGO_SETTINGS_MODULE=config.settings.dev` и `GW_ENVIRONMENT=dev`. Вход `admin` / `admin` из `DJANGO_SUPERUSER_*`. Приложение: http://localhost:8080, Swagger шлюза: http://localhost:8080/gw/docs, админка Django: http://localhost:8080/admin/.

На сервере нужны `config.settings.prod` и `GW_ENVIRONMENT=prod`. Процесс не стартует, если `DJANGO_SECRET_KEY`, `INTERNAL_TOKEN`, `DJANGO_ALLOWED_HOSTS=*` или пароль суперадмина `admin` остались заготовками из примера. `INTERNAL_TOKEN` и `GW_INTERNAL_TOKEN` должны совпадать. Документация `/gw/docs` в prod выключена.

При старте backend применяет миграции, загружает фикстуры (`debt_group_scale`, `bnp_dictionaries`, `notary_offices` — 218 нотариальных контор с belnotary.by, `message_templates` — шесть каркасов писем по группам долга 1–6) и создаёт суперадминистратора. Каталог `../Примеры данных` монтируется в контейнер как `AIS_SPEC_DIR`. Если Docker не смог смонтировать путь с кириллицей, интерфейс всё равно открывается, не работает только сверка импорта со спецификациями.

Загрузка обезличенной тестовой выборки (четыре схемы: BR2000, GR5000, MG6000, MN7000; файлы лежат в `backend/fixtures/ais_sample`, это те же 16 CSV, что в «Тестовая выборка для тестов»):

```powershell
docker compose exec backend python manage.py load_ais_sample
docker compose exec backend python manage.py link_territories
```

Полная замена: `reload_ais_sample` удаляет все карточки лицевых счетов, мероприятия и узлы карты, пользователей не трогает, и заново читает только 16 файлов выборки тем же импортом, что экран «Загрузка АИС» (`AisImporter`). После импорта у счетов с долгом появляются мероприятия.

```powershell
docker compose exec backend python manage.py reload_ais_sample
docker compose exec backend python manage.py link_territories
```

Без Docker, из каталога `app\backend`:

```powershell
..\.venv\Scripts\python.exe manage.py load_ais_sample
..\.venv\Scripts\python.exe manage.py link_territories
```

После обновления справочника улиц `link_territories` нужен один раз: уже загруженные счета перекладываются на город и точку из справочника. Новый импорт делает это сам.

## Локальный запуск без Docker

```powershell
cd app
uv venv .venv --python 3.11
uv pip install --python .venv -r backend/requirements.txt -r backend/requirements-dev.txt -r gateway/requirements.txt -r gateway/requirements-dev.txt

# backend (без POSTGRES_HOST используется SQLite)
cd backend
$env:INTERNAL_TOKEN="dev"; $env:GATEWAY_URL="http://127.0.0.1:8001"; $env:BACKEND_PUBLIC_URL="http://127.0.0.1:8000"
..\.venv\Scripts\python manage.py migrate
..\.venv\Scripts\python manage.py loaddata debt_group_scale bnp_dictionaries notary_offices message_templates
..\.venv\Scripts\python manage.py createsuperuser
..\.venv\Scripts\python manage.py link_territories
..\.venv\Scripts\python manage.py runserver 127.0.0.1:8000

# gateway (в другом терминале)
cd gateway
$env:GW_BACKEND_URL="http://127.0.0.1:8000"; $env:GW_INTERNAL_TOKEN="dev"
..\.venv\Scripts\python -m uvicorn app.main:app --port 8001

# frontend (в третьем терминале) — http://localhost:4200, прокси /api и /gw
cd frontend; npm install; npm start
```

## Фильтр, настройки, печатные формы и комплект нотариуса

- Замечания главы 3. Реестр договоров открывают суперадминистратор, локальный администратор, наблюдатель, специалист «Просмотр» (роль `viewer`) и контур поставщика. Специалист начисляющей организации и специалист ЮС получают 403. В списке только услуги с долгом (`balance_out`, пеня или просрочка больше нуля); карточка услуги без долга по id открывается. Группа `0` в фильтре и в ручном выборе — нет группы или вручную поставленный ноль. «ID договора» — `service_list_id`, «Номер договора» — отдельное поле `agreement_number` (пусто, пока колонки нет в выгрузке). Срок погашения на гриде — день месяца (`payment_due_day`, иначе день из настроек расчёта, обычно 25); дата `repayment_due_on` в базе остаётся. Канбан: номер ЛС, полный адрес, месяцы долга, пометка «долг с …». Если услуг с долгом больше одной, подпись услуги добавляет их число. Срез «Поставщики» виден суперадминистратору и локальному администратору; кнопка «Лица» снята, у остальных список открывает услуги. Заголовок столбца услуг перетаскивается. Панель фильтра не шире окна. Карточка договора — вкладки: общие (блок ЛС и блок договора, категория и наследство), регистрация, контакты, мероприятия, услуги этого поставщика по ЛС, остатки по периодам, история таблицей «Когда / Что / Было / Стало / Основание». «Обновить сейчас» пересчитывает ЛС. Поставщик на своей услуге ставит предупреждение, отключение и дополнительное мероприятие. Начисляющая организация приостанавливает мероприятие (`POST /api/v1/measures/{id}/hold/` с датой и причиной, `POST /api/v1/measures/{id}/release/`). Дополнительное мероприятие: справочник `GET/POST/PATCH/DELETE /api/v1/nsi/extra-measures/` (пишет администратор), на выбранные ЛС — `POST /api/v1/accounts/extra-measures/`, на услугу договора — `POST /api/v1/contracts/{id}/extra-measure/`. Смерть плательщика ставит `payer_deceased`, ставит открытые мероприятия на паузу и пишет во входящие; новый плательщик снимает эту паузу. Незанятый в экономике получает категорию `ais-17`, выехавший за пределы РБ — `ais-08`. Число на вкладке «Регистрация» — только действующие строки. Кнопка столбцов карточки ЛС называется «Настройки таблицы». Ручная группа и категория стоят под своими карточками. Проверки — `tests/test_chapter3_remarks.py`. Миграции `debts.0035`, `users.0009`, `nsi.0017`.
- Замечания главы 2. Реестр ЛС запускает мероприятия, меняет сценарий из справочника (`POST /api/v1/accounts/change-scenario/`) и передаёт счета специалисту ЮС (`POST /api/v1/accounts/assign-legal/`, роль `legal`). «Запустить сценарий» — `POST /api/v1/accounts/start-scenario/`. Если ничего не отмечено, действие идёт по текущему фильтру. У обслуживающей организации режим `manual` (по умолчанию) или `auto`: `GET/PATCH /api/v1/service-organizations/{id}/scenario-mode/`. Базовый сценарий открывает обзвон, СМС и уведомление с 0 месяцев, предупреждение с 2 месяцев, а отключение, надпись, иск и ОПИ — через 5 дней после даты вручения, если долг не погашен. Успешный дозвон (прослушано не меньше 70%) закрывает только попытку этого дня; пока `GW_VOICE_MODE=stub`, набор не выполняется. Долг 0 закрывает меры и сценарий с основанием «Долг оплачен». Фильтр группы `0` — счета без группы. Календарь добавляет задачи этих триггеров и заметки схемы (`POST /api/v1/accounts/calendar-notes/`). Проверки — `tests/test_chapter2_remarks.py`. Миграции `users.0007`, `nsi.0015`, `debts.0031`.
- Реестр ЛС: пока открыты фильтр, столбцы, мероприятие, смена сценария или передача в ЮС, кнопки панели сжимаются до коротких подписей («Меропр.», «Сценарий», «Запуск», «ЮС», «Столб.»), а панель фильтра занимает до 960px и не ломает названия столбцов. Карточка ЛС открывается по `GET /api/v1/accounts/{id}/`. Услуги, регистрации и категории догружаются следом и не держат шапку. Остальные вкладки запрашивают свои данные в момент открытия. Список ЛС считает число услуг и суммы отдельными подзапросами и не группирует исходный JSON выгрузки. Услуги карточки забирают периоды одним запросом, без JSON `raw`. Мероприятия одного ЛС не обходят всю схему. Миграция `debts.0032` добавляет B-tree индексы на счёт и номер, этап, услугу и поставщика, период долга, оплату, регистрацию, историю, частное мероприятие и дело. На вкладке «Вложения» у файла и документа пакета есть «Открыть» и «Скачать»: файл счёта — `GET /api/v1/attachments/{id}/download/`, документ пакета — `GET /api/v1/claims/{id}/package/documents/{id}/pdf/`. Строка работы без файла остаётся записью.
- Поиск в реестрах ЛС, договоров, мероприятий и претензионно-исковой работе не группирует JSON выгрузки. Суммы поставщика и число услуг — отдельные подзапросы. Реестр мероприятий считает группы без обхода всех партий, а имя должника добирает только у показанных строк. Уже связанное дело при открытии реестра не переписывается. Справочник организаций ждёт паузу ввода, как остальные поиски. Миграция `debts.0033` добавляет gin_trgm-индексы на номер ЛС, плательщика, схему, сценарий, услугу и шаблон мероприятия: обычный B-tree поиск по части слова не ускоряет.
- Пользовательский фильтр реестров ЛС, договоров, мероприятий и претензионно-исковой работы строится строками: поле, оператор, значение, объединение «всем» (И) или «любому» (ИЛИ), вложенная группа и флаг «кроме» (НЕ). Список принимает `domain` JSON и применяет его вместе с остальными фильтрами. Поля — только те, что реестр уже умеет отбирать. Набор пишется в сохранённый фильтр пользователя.
- Смена своего пароля открывается значком настроек в шапке рядом с учётной записью (`/password`: текущий пароль, новый и повтор). `POST /api/v1/auth/password/` после успеха пишет аудит без самого пароля.
- Настройка разложена вкладками: «Правила рейтинга и групп», «Организации и пользователи», «Сценарии и шаблоны», «Интеграции». Справочник дополнительных мероприятий — `/settings/work/extra`, его пишет суперадминистратор и локальный администратор. У сценариев свои вкладки и адреса: `/settings/work/scenario` и `/settings/work/forms`. На странице сценария порядок шагов остаётся на подвкладке «Сценарий», условия каждой меры — на подвкладке с её названием. Экрана «Шаблоны сообщений» нет: `/settings/work/messages` и `/templates` открывают печатные формы. «Интеграции» (`/settings/integrations/…`) — субвкладки каналов: SMTP, Asterisk AMI, SMS, мессенджеры, Белпочта, АИС ПРИС, ЛК БНП, АИС «Расчет-ЖКУ». Каталог и статус — `GET /api/v1/integrations/`, `GET /api/v1/integrations/{code}/`. Почта схемы (отправитель, тема, подпись) и номера обзвона схемы правятся на SMTP и Asterisk; из сценария оставлены ссылки. Хост SMTP и AMI в UI не задаются — только в окружении шлюза. Новый канал добавляется записью в `apps/nsi/services/integrations.py` и субвкладкой на экране.
- «Печатные формы» (`/settings/work/forms`) — визуальный конструктор на листе A4 с компактной панелью форматирования в стиле Word и строгим чёрно-белым оформлением официальных документов АИС «Расчет-ЖКУ». На верхней ленте выбираются гарнитура шрифта (`Times New Roman`, `Arial`, `Calibri`, `Georgia`, `Verdana`, `Tahoma`, `Courier New`, `DejaVu Serif`, `DejaVu Sans`), размер (`8–36` пт), жирное и курсивное начертание, выравнивание (`слева`, `по центру`, `справа`, `по ширине`), ширина блока, поле ЛС из выпадающего списка `+ Поле ЛС…`, а также операции с блоками и таблицей активного блока. Панель структуры блоков открывается по кнопке «Структура». На самом листе A4 нет лишних панелей и голубой окраски; столбцы таблиц и блоки меняют ширину и порядок перетаскиванием. Пользователи могут создавать собственные шаблоны («+ Новый шаблон», «+ Добавить» в списке «Мои шаблоны», «Сохранить как свой шаблон») с автоматической генерацией уникального кода из названия. Бланки предупреждения (r99116), напоминания (r99140), уведомлений по ст. 137, 80 и 87, 86 ЖК и по обращению с ТКО (r99189, r99188, r99190, r99191), расчёта задолженности (r99117), а также официальные макеты доверенности, заявления на исполнительную надпись и трёх исков раскладываются в редактируемые блоки (`blank_to_blocks`) и сохраняют совместимость со сборкой по образцу. PDF собирает WeasyPrint; если библиотека не загрузилась, остаётся текстовый сборщик fpdf2. `GET /api/v1/nsi/print-forms/blank-data/?blank=&account=` отдаёт текст бланка, поля счёта, список частей и блоки конструктора. Миграции `nsi.0011` и `nsi.0012`. Кнопка «Загрузить скан/PDF» читает текстовый слой PDF (pypdf), документы `.docx` и текстовые файлы, раскладывая шапку, заголовок, абзацы и таблицы в блоки листа A4 (технические колонтитулы печати отсекаются). Файл без текстового слоя остаётся пустым черновиком, байты PDF в макет не попадают. Законы и инструкции из папок АИС ИДО, исполнительного производства и нотариальной надписи в макет не копируются: это справочные файлы, не бланк лицевого счёта.
- Карточка дела (`/claims/{id}?tab=pack`) открывается на вкладке «Комплект»: слева перечень документов, справа поля выбранной строки. Остальные вкладки той же карточки: «Нотариат», «Суд», «ОПИ», «Списание». Дата вручения предупреждения и нотариальный тариф пишутся в дело сразу (`PATCH /api/v1/claims/{id}/`): смена вкладки, другого пункта комплекта и загрузка документа их не стирают. Реестр при открытом деле не показывается. Форма должников и строк задолженности личного кабинета БНП на экран не выводится: сведения берутся из лицевого счёта. «Собрать архив» заново читает личный номер из регистрации плательщика. Номер — 7 цифр, латинская буква, 3 цифры, 2 латинские буквы и цифра, например `4111111A111AA1`. Четырнадцать цифр без букв не подходят. «Собрать архив» вызывает `POST .../package/` и `POST .../package/form/`. В комплекте и во вкладке «Суд» встроенный редактор листа не дублируется: кнопка «Просмотреть» показывает готовый PDF на месте, а кнопки «Создать» и «Открыть в редакторе печатных форм» переводят специалиста в конструктор `/settings/work/forms` с привязкой к делу и документу (`claim`, `doc`, `form`, `pane=layout`) и подстановкой реквизитов ЛС. `POST /api/v1/claims/{id}/package/from-template/` и `POST .../package/documents/{id}/layout/` собирают локальный PDF. Шаг сценария «Исполнительная надпись» открывает дело на том же мероприятии взыскания и подставляет PDF из печатных форм заявления, расчёта, доверенности и предупреждения. На комплекте кнопки «Подписать документы заявителя» и «Подписать доверенность» (`POST .../sign-documents/`, отсоединённый PKCS#7 от плагина AvCMXWebP), «Собрать архив» (`POST .../package/form/`, zip пишется сразу и скачивается, специалист возвращается на карточку ЛС), «Скачать архив», «Скачать json» и неактивная «Отправить»: обмен с БНП система-система не подключён. Пустой вызов без подписи отметку не пишет. `POST .../sign-and-send/` требует уже сохранённый PKCS#7, пишет zip и номер заглушки. В кабинет БНП вызов не ходит. Правка PDF снимает подпись и архив.
- Реестр претензионно-исковой работы делится на «Нотариат», «Суд» и «ОПИ». Нотариальная контора выбирается из справочника палаты `GET /api/v1/nsi/notary-offices/` (название, округ, адрес, телефоны); вписанное название тоже сохраняется в `notary_office`. Подразделение ОПИ выбирается из справочника `GET/POST/PATCH/DELETE /api/v1/nsi/opi-offices/` (25 подразделений РБ и локальные записи схемы, миграция `nsi.0018`). Снятая с публикации контора или подразделение ОПИ из списка пропадает, запись в НСИ не удаляется. Список, канбан, календарь и график запрашивают `claim_module=notary`, `court` или `opi`. Перенос карточки дела проверяет документы колонки, в которую её кладут: без файла карточка остаётся на месте и открывается окно с переходом на вкладку «Комплект», «Суд», «ОПИ» или «Исполнительная надпись». Комментарий отказа нотариуса заменяет скан постановления. Меры, которые АИС ПРИС уже вернула в карточку, файл постановления не требуют. ОПИ и итог есть на вкладках нотариата и суда, а вкладка `opi` сводит все дела на стадиях принудительного исполнения (`writ_done`, `court`, `opi`, `opi_measures`, `recovered`, `impossible`, `writeoff`). Комментарий нотариуса пишется в `notary_note`, примечание к иску — в `lawsuit_note`. Расчёт из шаблона и загруженный файл расчёта — два PDF, один не затирает другой. В строке задолженности одновременно период и одна дата не сохраняются. Исковый PDF (взыскание, выселение, отчуждение) хранится в комплекте и в манифест БНП не входит. Повторное открытие дела по тому же ЛС возвращает уже созданное. Несколько надписей за разные периоды остаются разными пакетами: на вкладке «Исполнительная надпись» карточки ЛС, в колонке «Дело» списка претензий и переключателем на карточке дела. Клик по должнику в претензионно-исковой работе открывает надпись с периодом. Если такой надписи нет, дело без периода не открывается и не создаётся: в колонке «Дело» написано «не заведена», а на экране — что надпись создаётся кнопкой «Добавить исполнительную надпись». Старое дело без периода по-прежнему видно на вкладке карточки ЛС. Строка пакета на карточке ЛС свёрнута: треугольник слева и щелчок по названию раскрывают состав, справа кнопки «Перейти в пакет» и «ОПИ». У каждого свой комплект: почта и архив одного пакета в другом не появляются. История дела показывает новые записи сверху. Карточка канбана та же, что в реестре ЛС: имя, овал «рейтинг-группа» (например A/1-1), номер и адрес, сценарий, собственность и жилфонд. Месяцы, проживающие и зарегистрированные — справа от этих строк. Сумма долга, основной долг и пеня — в левом нижнем углу, кружок специалиста справа в той же полосе. Срок, если он есть, стоит между суммой и кружком. Под сценарием остаётся этап дела и, в нотариате, переход в суд.

## Устройство

### Данные АИС («Примеры данных»)

- Файлы `Примеры данных/*.csv` — это спецификации полей Oracle-выгрузки (`COLUMN_NAME;DATA_TYPE;COMMENTS;MODULE_NAME`, cp1251), а не сами данные. Модели `Account`, `AccountService`, `Payment`, `Registration` построены по ним и остаются плоским слоем импорта.
- Нормализованная схема PostgreSQL (не ниже 3НФ) по тем же спецификациям — `postgres/ais_3nf.sql`, схема `ais`. Django её не мигрирует. Пустой контейнер PostgreSQL создаёт эти таблицы при первом старте. Повторный запуск скрипта остановится, если схема уже есть; снос — `DROP SCHEMA ais CASCADE`.
- Карта колонок: `backend/apps/imports/field_maps.py`. Повторяющиеся имена (`ACCOUNT_ID`, `ATTR_VALUE`, `FULL_NAME`, `CLIENT_ACCOUNT`) разводятся по порядку следования и `COMMENTS`. Колонка «Тип оплаты» без имени читается из заголовка `PAYMENT_TYPE`. Соответствие карты спецификациям проверяет тест.
- Импорт (`POST /api/v1/imports/` до 50 МБ или `manage.py import_ais` для полной выгрузки):
  - в интерфейсе раздел «Загрузка АИС» в левом меню. Суперадминистратор и локальный администратор выбирают один или несколько файлов. Тип узнаётся по началу имени («Карточка ЛС», «Услуги», «Оплата», «Регистрация»), сначала отправляются лицевые счета. Суперадминистратор выбирает схему или заводит новую на том же экране (`POST /api/v1/organizations/`). Локальный администратор грузит только в свою схему. Специалист и наблюдатель файл не загружают;
  - CSV (UTF-8 или cp1251, разделитель `;`, таб или запятая) и Excel (`.xlsx`, `.xlsm`, `.xls`, первый лист);
  - заголовки — либо `COLUMN_NAME` из спецификации, либо русские названия отчёта (`backend/apps/imports/header_aliases.py`). Колонка «Учетный номер плательщика» в файле регистрации пишется на лицо. Если плательщик — юридическое лицо, номер попадает в УНП лицевого счёта и виден в реестре ЛС. В ночной выгрузке без этой колонки УНП юридического лица по-прежнему берётся из идентификационного номера паспорта;
  - подписи полей из выгрузки в реестре, карточке и выгрузке CSV совпадают с заголовками файлов выборки `fixtures/ais_sample` (рейтинг, этап воронки, группа, сценарий и специалист остаются названиями ПМ);
  - CSV команда читает потоком и пишет пакетами по 500 строк (`bulk_create` / `bulk_update`); книга Excel читается целиком;
  - upsert по ключу; повтор одного ключа внутри пакета оставляет последнюю строку;
  - повторная загрузка того же лицевого счёта обновляет поля, которые в файле изменились. Строка без изменений дубль не создаёт и в журнале считается «без изменений»;
  - строки чужой схемы отклоняются;
  - журнал пишется в `ImportJob`;
  - после импорта ЛС, услуг, оплат и регистраций пересчитываются группа, дата возникновения, рейтинг, сценарий, этап воронки и контакты из АИС, пакетами по 500 лицевых счетов. Ручная группа хранится отдельно и снимается, только если расчётная группа изменилась относительно основания корректировки. Счёту с группой долга назначается опубликованный сценарий схемы, а если своего нет — «Стандартное взыскание». Типовой сценарий идёт по порядку: автообзвон, уведомление, предупреждение, исполнительная надпись, исковое заявление. Смена группы не снимает открытое мероприятие и не перескакивает на шаг старшей группы. Свой сценарий схемы по-прежнему может ветвиться по группе. Рейтинг A–E считается из группы: группы 1–2 — A, группа 3 — B, группы 4–5 — C (при отягчающих обстоятельствах D), группа 6 — E. Название сценария группы на карточке ЛС не подменяет название шага в реестре мероприятий. Пропуск текущего шага — `POST /api/v1/accounts/{id}/skip-step/` с причиной: это может администратор или специалист с признаком `can_approve`. Тот же признак нужен, чтобы сменить этап воронки и перетащить карточку мероприятия. Отключение само не стартует, пока предупреждение не вручено. Если шаг не может начаться, строка всё равно есть со статусом «Завершено с ошибкой» и причиной. Открытие реестра добирает счёт с группой долга без мероприятия и повторяет сорвавшийся обзвон. Открытый автообзвон остаётся текущим шагом. Название шага в реестре не подменяется названием сценария группы на карточке. Исполнитель взыскания — закреплённый специалист этого счёта, а если он не указан — специалист начисляющей организации той же схемы. Автообзвон исполнителя не требует. Если специалиста в схеме нет, строка всё равно создаётся со статусом «Назначено», колонка исполнителя пустая. Ручной запуск взыскания из реестра по-прежнему требует выбрать исполнителя. Дело взыскания — отдельная строка «Взыскание» с названием этапа (подготовка, нотариус, отказ, иск, суд, ОПИ). Открытие реестра мероприятий само добирает такие строки по уже загруженным счетам, повторная загрузка файла для этого не нужна. Наследственное дело автомеру не ставит.
- Исходная строка сохраняется в `raw`. `manage.py purge_retained` очищает `raw` старше `RAW_RETENTION_DAYS` (по умолчанию 90), `AuditLog` старше `AUDIT_RETENTION_DAYS` (365) и `ErrorLog` старше `ERROR_LOG_RETENTION_DAYS` (90). Команду ставят в планировщик, она не вызывается на каждый запрос.
- Списки лицевых счетов опираются на индексы `(organization, provider_id, debt_group)` и `(organization, balance_out)`. На PostgreSQL миграция `0005_pg_trgm` создаёт расширение `pg_trgm` и GIN-индексы по ФИО, адресу и идентификационному номеру. Роли БД нужно право `CREATE EXTENSION`, иначе расширение создают один раз отдельно и миграцию прогоняют снова.
- В спецификации `DEBT_PERIOD` имеет тип DATE, но по описанию это число месяцев долга. Хранится как целое, это стоит уточнить у команды АИС.
- Тариф и количество по услуге хранятся с десятью знаками после запятой: в отчёте встречаются значения вроде `0,20745` и `1,3333333333`.
- Обезличенная выборка `backend/fixtures/ais_sample`: 160 лицевых счетов, 2974 договора услуг, 69 оплат, 792 регистрации. В файлах остались следы Excel: УЕН записан как `1,2E+11`. Целое из этой записи сохраняется в `unified_account` (для `1,2E+11` это 120000000000). Уже загруженный счёт без числа показывает текст УЕН из `raw`. Часть телефонов в том же виде остаётся текстом в `raw`. «Доля по документу» местами выглядит как `01.янв`; «Статус пачки» и «Способ распределения» — слова, не коды, они остаются в `raw`. Девять договоров повторяют один ID услуги с разными названиями, сохраняется последняя строка. У GR5000 во всех услугах «Кол-во периодов долга» равно 0, поэтому группа не поднимается выше 1.

### Реестр и карточка (ТЗ 4.2.1, 4.2.2)

- Реестр ЛС: серверный список (колонки включают числовой код ЛС, ИН и УНП отдельно), канбан по этапу воронки. При входе открывается канбан, иконка канбана первая в общей группе видов (канбан, список, календарь, карта, графика). Колонки основной ветви: «Новый должник», «Автообзвон», «Уведомление/Предупреждение», «Отключение услуг», «Подготовка пакета на исполнительную надпись», «Направлено нотариусу», «Исполнительная надпись совершена», «Отказ нотариуса», «Исковое заявление в суд», «Судебное решение получено», «Направлено в ОПИ», «Меры ОПИ приняты», «Взыскано», «Невозможность взыскания», «Подготовка документов о списании безнадежной задолженности». «Предупреждение вручено» колонкой не является. Уведомление о выселении и выселение колонками не ставятся: это параллельная ветвь групп 4–6. Карточка стоит в колонке сохранённого этапа. Открытое мероприятие другого этапа остаётся бейджем «мероприятие · статус» и в счётчик старой колонки не входит. Щелчок по бейджу открывает вкладку «Активности» и этап не меняет. Доска занимает окно под строкой реестра. Подписи колонок одной высоты: по вертикали по центру, по горизонтали по ширине столбца. Окно браузера не прокручивается. У доски один ползунок справа, у столбцов своих ползунков нет. Длинная карточка листается под шапкой. Вбок доска листается тем же ползунком. Карточку можно отпустить в любое место колонки, в том числе в пустую часть под карточками. На карточке канбана: ФИО, номер ЛС и адрес, один овал справа в строке с ФИО: рейтинг и группа через дефис, например A/1-1 (буква, подрейтинг и группа задолженности). В списке колонки рейтинга и группы остаются отдельными, название сценария одной строкой без перечня шагов, закреплённый специалист, тип собственности, тип объекта жилфонда, месяцы долга, проживающие и зарегистрированные, сумма задолженности, сумма основного долга и сумма пени из той же суммы `balance_mulct_out`, что и колонка списка. Месяцы долга, проживающие и зарегистрированные стоят справа от сценария и типа жилья. Сумма задолженности, основной долг и пеня стоят в левом нижнем углу, кружок специалиста — справа в той же полосе. Пустой ряд под суммами не остаётся. Кружок с инициалами — закреплённый специалист, подсказка называет его. Номер и дата договора, поставщик услуги, первоначальные суммы задолженности и пени, остатки по периодам, срок погашения по договору, дата последней оплаты, количество услуг с задолженностью и наиболее ранний период возникновения долга остаются столбцами грида и не повторяются на карточке канбана. Адрес в списке и группировке лицевых счетов пишется целиком, окно списка тянется до низа страницы и прокручивается внутри. Заголовок столбца — короткая подпись в несколько строк, полное название видно при наведении. Ширина столбца равна самой длинной ячейке на экране. На вкладке «Услуги» карточки выбор столбцов открывается списком под кнопкой «Столбцы». В остальных ячейках, где больше двух слов, список, группировка, канбан и срез услуг показывают первое слово. Полный перечень договоров и поставщиков остаётся на карточке. Суммарный долг по всем услугам ЛС подписан отдельно. В списке и группировке знак белорусского рубля стоит в заголовке денежного столбца (основной долг, пеня, суммарный долг, первоначальные суммы, остатки по периодам), в ячейках только число. Группировка по схеме, обслуживающей организации, группе задолженности и остальным полям панели открывает тот же список лицевых счетов под сворачиваемыми шапками: название группы, число ЛС и сумма задолженности справа, под шапкой те же столбцы грида. Внизу итог: число ЛС, услуги с задолженностью, основной долг и пеня. «Показать ещё» дочитывает группу (`group_by` и `bucket`, пустое значение — `bucket=__blank__`). Смена этапа воронки — перетаскивание карточки в любое место столбца, включая пустое место под карточками. Карточка при движении видна целиком, за курсором следует её копия. Текст страницы при переносе не выделяется. Основание не спрашивается. Если для перехода не хватает даты вручения предупреждения или документа, карточка остаётся в своей колонке, а поверх доски открывается окно: список недостающих документов и кнопка «Перейти на вкладку …». При шаге вперёд проверяются файлы этапа, с которого карточку забирают, и документы колонки, в которую её кладут: PDF предупреждения для отключения, расчёт, заявление и доверенность для нотариуса, исполнительная надпись, отказ нотариуса, судебное решение, исполнительный документ для ОПИ, файл меры ОПИ, акт о невозможности взыскания. Параллельная ветвь выселения требует файл уведомления о выселении. Ответ такого отказа — код `funnel_gate`. Плашка ошибки сверху при таком отказе не появляется. Запись попадает в историю: дата, пользователь, старый и новый этап. Это не замена мероприятия. Несколько отмеченных карточек переносятся вместе. Наблюдатель и поставщик этап не меняют. Кнопка «Столбцы» включает и выключает отдельные колонки списка, набор и порядок сохраняются у пользователя (`GET/PUT /api/v1/accounts/columns/`, в ответе поле `order`). Сроки на календаре — крайний срок действия по конкретному лицевому счёту: подпись называет счёт и действие, а не одно слово «предупреждение». Если срок прошёл, а действие не выполнено, запись красная и остаётся на доске; срок вне видимого месяца встаёт на сегодняшнюю клетку. Срок через один или два дня жёлтый. Выполненное действие на своей дате красным не красится. В месяце и неделе в клетке одна короткая сводка: сколько сроков, сколько из них просрочено или наступает в ближайшие два дня. Группировка по организации, группе задолженности, рейтингу должника, категории, закреплённому специалисту, типу собственности, типу объекта жилфонда, месяцам долга, числу проживающих или месяцу возникновения долга. Фильтры специалиста, собственности, жилфонда, месяцев, проживающих и периода с/по доступны всем ролям, не только через «добавить фильтр». Экспорт CSV. Кнопка «Назначить» создаёт мероприятие по отмеченным счетам, а если отметки нет — по всем счетам текущего фильтра. Шаблон выбирается из действующих (`GET /api/v1/templates/`), в партию пишется его название. Поставщик, а также отключение и взыскание, отмечают виды услуг из `GET /api/v1/services/choices/`; запуск передаёт `catalog_service_ids`, и сервер берёт строки этих услуг на счетах фильтра. Канал уведомления в этой панели — только SMS или e-mail. Набор колонок по-прежнему читается с сервера, чекбоксы колонок со страницы убраны. Обзвон передаёт шаблон, окно времени и CSV с номером по правилу источника. Уведомление выбирает канал и шаблон. Предупреждение сохраняет PDF. Отключение и взыскание требуют отмеченные услуги, а не все услуги ЛС. Взыскание создаёт задание исполнителю и срок. Смена сценария берёт название и дату начала.

Миграция `debts.0034` добавляет `parallel_stage` и активности и переименовывает старые коды этапа (`prevention` → `call`, `warning` → `notice`, `enforcement` → `prep`, `court` → `opi`, `closed` → `recovered`). Число комнат и проживающих — на вкладке «Общие». Сумма задолженности и пеня на вкладке «Общие» одним шрифтом, пеня — сумма `balance_mulct_out`. Наследство и банкротство стоят в блоке признаков. У чек-листа исполнительной надписи есть полоса прогресса, кнопка пакета остаётся неактивной до закрытия всех пунктов. В реестре группа и рейтинг выводятся цветными бейджами. Карточка канбана: полоса цвета группы слева, значки рейтинга и группы (название — в подсказке), значения без повторяющихся подписей. Месяцы и люди — справа от сценария, суммы основного долга и пени разным цветом в левом нижнем углу, кружок с инициалами закреплённого специалиста справа (имя — в подсказке). Дата, если есть, между суммой и кружком. Реестр мероприятий повторяет макет: строка поиска с чипом периода («июль 2026»), флажки строк, группы статусов в одной таблице, статус «Выполняется» сиреневый, у ошибки короткая подпись «Ошибка», под таблицей матрица по типам — дата или слово в цветной плашке. Календарь один на реестрах лицевых счетов, договоров, мероприятий и претензионно-исковой работы: сетка дня, недели и месяца, плашка «вид — должник» по группе задолженности, справа три карточки (группы, типы, подсказка). Фильтр реестра: три колонки и окно «Добавить пользовательский фильтр» с условиями «и» / «или» / «кроме». Карточка мероприятия красится по виду (обзвон, письмо, предупреждение, отключение). Знак белорусского рубля рисует интерфейс: буква «Б», горизонтальная черта на четверти высоты снизу режет округлую часть пополам. Готового знака в шрифтах нет. Знак стоит в заголовке денежного столбца или в подписи показателя и по размеру совпадает со шрифтом строки. В ячейке только число.
- Реестр договоров (`/contracts`): единица учёта — поставщик услуги. При входе открывается канбан с теми же колонками матрицы, что у реестра ЛС. Срез «Поставщики» остаётся в переключателе списков: по каждому поставщику количество ЛС с задолженностью, сумма основного долга, сумма пени, суммарная задолженность, мероприятия и претензионно-исковые действия по этим счетам. Группа на срезах «Лица» и «Услуги» и колонка канбана поставщика берутся по услуге, а не по старшей группе всего лицевого счёта. На гриде услуг: номер ЛС, адрес, ID договора, дата, номер договора, услуга, группа, рейтинг, этап, сценарий, дата возникновения, суммы, день срока погашения, последняя оплата, плательщик, ИДНУНП, организация, поставщик, категория, специалист, собственность, жилфонд, период, проживающие и зарегистрированные. Остатки по периодам в этот каталог не входят. Карточка канбана: номер ЛС, полный адрес, месяцы долга и пометка «долг с …». Если услуг с долгом больше одной, к названию добавляется их число. Реестр договоров специалисту начисляющей организации и специалисту ЮС закрыт. Перенос карточки доступен администратору. Запрещённый правилами переход карточку не двигает. Если не хватает даты вручения предупреждения или документа колонки, открывается то же окно, что на канбане лицевых счетов: действие и переход на вкладку карточки, а не плашка ошибки сверху. Поставщик и наблюдатель этап не меняют. Названия действий приходят готовыми (`GET /api/v1/contracts/summary/`, у строки `suppliers` и у общих `measures`/`claims` есть `label`). Чужое мероприятие и документ по чужой услуге в строку не попадают. Дело взыскания по лицевому счёту видно поставщику, у которого на этом счёте есть долг. Щелчок по строке открывает услуги этого поставщика (`provider_id`). Срезы «Лица» и «Услуги» остаются: список лиц с ИН и УНП отдельно. Кнопка «Столбцы» на срезах «Лица» и «Услуги» прячет лишние колонки и при включении возвращает столбец на место, с которого его убрали (`GET/PUT /api/v1/contracts/columns/?board=persons` или `services`), числом ЛС, суммой и ранним периодом, список услуг, канбан по этапу с той же плотностью, что у карточки лицевого счёта: плательщик, ИН или УНП, число ЛС и услуг, название услуги, улица, группа, категория, долг и пеня, срок погашения или дата возникновения долга. Карточку перетаскивают левой кнопкой в другую колонку или выбирают этап значком в углу: этап ставится всем лицевым счетам этого должника в видимом контуре и дальше не затирается пересчётом. Несколько карточек отмечают с Ctrl и переносят вместе. Наблюдатель и поставщик этап не меняют. Чужой счёт и несколько схем в одном переносе отклоняются (`POST /api/v1/contracts/stage/`). Календарь сроков погашения и контрольных дат — та же правая панель: виды отображения, выбор дня или диапазона. Запись — срок действия по лицевому счёту и услуге. Непогашенный просроченный срок красный и остаётся на доске, срок через один или два дня жёлтый. Пустые дни без срока в режиме дня не показываются. Фильтры реестра договоров совпадают с базовыми фильтрами реестра ЛС: группа задолженности, этап воронки, закреплённый специалист, тип собственности, тип объекта жилфонда, число месяцев долга, число проживающих и период возникновения долга. Событие открывает карточку, день на доске создаёт мероприятие по фильтру договоров (`POST /api/v1/contracts/events/`). «Фильтры» открывает панель поиска. строка поиска открывает панель «Фильтры / Группировать по / Избранное» (группы, категория, этап, обслуживающая организация по названию или коду, сохранённый набор). Группировка показывает лиц текущего отбора под теми же шапками, что реестр ЛС, а не сводную таблицу итогов: `GET /api/v1/contracts/persons/?group_by=&bucket=` отдаёт одну группу. Карточка договора открывается вкладками. «Общие» — блок лицевого счёта и блок договора (ID, номер, дата, услуга, поставщик, первоначальные суммы как основной долг и пеня, исходящее сальдо, день срока погашения, группа услуги, сценарий), ниже категория, проживание и наследство. «Регистрация» перечисляет лиц. «Контакты» совпадают с карточкой ЛС. «Мероприятия» показывают сценарий счёта, активные и завершённые шаги и ссылку в реестр; начисляющая организация приостанавливает шаг, поставщик формирует предупреждение и отключение только этой услуги и дополнительное мероприятие. «Услуги поставщика по ЛС» — таблица услуг того же поставщика на этом счёте, текущая строка зелёная. «Остатки по периодам» фильтруются годом и месяцем. «История изменений» — таблица со столбцами «Когда», «Что», «Было», «Стало» и «Основание», как на карточке лицевого счёта: группа и рейтинг, мероприятия и прочие изменения на отдельных кнопках. Этап воронки в «Было» и «Стало» пишется названием, не кодом. «Обновить сейчас» пересчитывает лицевой счёт. Правило обзвона (день месяца и часы только мобильного) задаётся в конструкторе сценариев, не на реестре договоров: реестр показывает сводку поставщика — сколько ЛС с долгом, суммы основного долга, пени и задолженности, какие мероприятия уже есть. Колонки «Схема», «Поставщик» и «Обслуживающая организация» показываются, только если в области пользователя таких организаций больше одной. Признаки приходят в `GET /api/v1/auth/me/` (`show_schema`, `show_supplier`, `show_service_org`). Суперадминистратор видит все три. Локальный администратор, специалист и наблюдатель одной схемы не видят колонку схемы: её имя уже в шапке; поставщика и обслуживающую организацию видят, если в схеме их несколько. Поставщик с одной организацией не видит своё имя в строках; если к нему привязано несколько поставщиков или его услуги сидят на счетах разных ЖЭС, соответствующие колонки остаются. Наблюдатель не запускает мероприятия, не правит карточку и не формирует отключение. Поставщик не меняет группу и не формирует задание на отключение: факт приостановления фиксирует он. Шаблоны сообщений в меню есть у начисляющей организации, которая их правит или отправляет. Поставщик не видит чужие услуги: пустой список его организаций означает пустой реестр, а не всю схему. Сальдо карточки ЛС (входящее, исходящее, начислено, оплата), группировка реестра, документы, вложения и мероприятия режутся по его `provider_id`. В составе долга ему видна только своя доля. Два поставщика ставят одно и то же мероприятие независимо: у партии пишется `owner_provider_id`, чужая партия в карточке ЛС и в реестре мероприятий не показывается. Смена сценария поставщиком запирает сценарий только его услуг. Общее мероприятие начисляющей организации (без поставщика-автора) по-прежнему видно, если в партии нет услуг или есть его услуга. Предупреждение и отключение с чужой услугой отклоняются, как и запись работы с задолженностью по чужой услуге. Поставщик не меняет группу, сценарий всего лицевого счёта, этап воронки и исполнителя. Факт приостановления и возобновления записывает только `POST /api/v1/measures/{id}/confirm/` с `action` `suspend` или `resume` и `source` `pm` или `ais`. `STOP_DATE` — дата окончания договора, пересчёт по ней приостановление не подтверждает. Поставщик создаёт обзвон, уведомление и предупреждение только с указанием своей услуги. Назначение категории сразу пересчитывает сценарий по правилу группа+категория. У специалиста начисляющей организации категория и наследственное дело расходятся на все ЛС с тем же ИН или УНП; у поставщика — только на счета, где есть его услуга. Пустые ИН и УНП не склеивают разных должников: канбан и список лиц считают одну карточку на ключ в SQL. Смена фильтра на открытом канбане, календаре или группировке запрашивает этот вид заново. Канбан договоров — одно дело на должника. Ответ канбана не включает остатки по периодам: карточка показывает название услуги и число услуг с долгом, периоды остаются на срезе «Услуги» и в списке лицевых счетов. Колонки собираются одним проходом, а не отдельным запросом на каждую. Контакт ПМ можно привязать к зарегистрированному лицу. Статус юрлица: действующее, ликвидация или банкротство. Наследственное дело ставит автомеры в «Приостановлено» и возвращает их в «Назначено», когда флаг снят, срок прошёл или в выгрузке появился новый плательщик. Исходящее сальдо услуги и пеня — разные колонки выгрузки; начальный долг копирует сальдо, начальная пеня — колонку пени.
- Группа услуги считается по числу месяцев до самого раннего непогашенного периода (`debt_period`). Весь остаток и пеня сидят на этом раннем периоде, поздние месяцы окна хранят ноль: в CSV нет суммы каждого месяца. Дата возникновения — день после срока оплаты раннего периода (`payment_due_day`, по умолчанию 25). Отключение и взыскание запускаются только по услуге группы 3 и старше; младшая услуга на том же счёте в партию не попадает. Обзвон один на счёт и отбирается по старшей группе счёта. Рейтинг A–E. Подрейтинг растёт при новом входе в ту же букву за `rating_period_months`, а не при каждой ночной загрузке. Без долга остаётся A без номера. D — группы 4–5 и признак «не занят в экономике» или банкротство. Правило сценария с категорией должника перекрывает правило группы. Центральный справочник категорий должника — 25 строк из «Основные документы/Категории должников.docx», других формулировок в нём нет: 7 базовых категорий АИС «Расчет-ЖКУ» и 18 часто используемых, в порядке документа. Прежние «Пенсионер», «Не занят в экономике», «Многодетная семья» и «Банкротство» выключены и в списке выбора не показываются; уже назначенная такая категория на карточке остаётся. Миграция `nsi.0016`. `GET /api/v1/nsi/debtor-categories/` без параметра `is_active` отдаёт только активные. Полное погашение снимает сценарий, в том числе назначенный вручную, и закрывает активные мероприятия. Параметры: `GET/PATCH /api/v1/nsi/calculation-settings/current/` (там же `warning_wait_days` — общий срок оплаты после вручения предупреждения, и `disconnect_requires_approval` — согласовывать ли отключение). У схемы свой срок: пустое `warning_wait_days` берёт общее значение, `step_waits` перекрывает дни ожидания шага. `GET/PATCH /api/v1/nsi/scenarios/timeline/`. Новая загрузка со сменой плательщика снимает флаг наследственного дела; пока он стоит, автоматические мероприятия не создаются. Ручная смена группы, если специалист закреплён, кладёт ему сообщение во входящие. Категории: `/api/v1/nsi/debtor-categories/`.
- Реестр мероприятий (`/measures`): при входе открывается канбан. Список сгруппирован по статусу (назначено, выполняется, завершено, ошибка, приостановлено, прервано). Канбан — те же шесть колонок. Доска занимает окно под шапкой реестра. Страница не прокручивается, у доски один ползунок справа. Подписи по центру по вертикали и по ширине столбца. Карточку можно отпустить в любое место колонки. Карточка как в реестре ЛС: должник и овал «рейтинг-группа» показанного ЛС (например A/1-1), номер ЛС, название шага, следующее действие и кружок исполнителя. Суммы и месяцы долга на этой карточке не повторяются. Карточку перетаскивает администратор или специалист с признаком согласования (`POST /api/v1/measures/{id}/status/`): статус партии и частных строк становится статусом колонки, основание «Перенос в канбане». Перед сменой статуса, кроме «Прервано» и «Завершено с ошибкой», проверяется файл вида: у предупреждения — PDF, у взыскания — расчёт, заявление и доверенность. Обзвон, уведомление, отключение, сценарий и дополнительное мероприятие файла не требуют. Если файла нет, карточка остаётся в колонке и открывается окно с переходом на вкладку, где документ прикладывают (`funnel_gate`). Колонка «Приостановлено» частные строки не меняет, следующий шаг сценария сам не стартует. Обычный специалист, наблюдатель и поставщик колонку не меняют. Щелчок по карточке открывает её. Флажок отмечает строку: скачивание берёт отмеченные, а если отметок нет — все видимые. Срок оплаты после предупреждения (свой у схемы, иначе общее `warning_wait_days`, базово 5 дней) написан на экране «Готовы к отключению» (иконка рядом со скачиванием). Кнопка скачивания собирает CSV. Календарь этого реестра — месяц с плашками мероприятий, переключатели «День / Неделя / Месяц» и боковая панель групп и типов. В событие календаря добавлено поле `debt_group`. В строке — название из вида и шаблона, должник и номер ЛС из видимого контура, исполнитель, следующее действие по статусу и сроку. Поиск `search` идёт по номеру ЛС, ФИО, шаблону, сценарию и примечанию. Вид находится по началу названия, если в запросе не меньше четырёх символов. `period=ГГГГ-ММ` оставляет мероприятие, чей срок пересекает месяц; без даты окончания оно остаётся в месяце начала. У завершённого в колонке «Следующее действие» написано «Завершено», срок — отдельной фразой; дата отключения и возобновления берётся из факта. «Показать ещё» дочитывает группу (`status` и `offset`, по 40) и матрицу (`offset`, по 200): `GET /api/v1/measures/registry/` и `GET /api/v1/measures/matrix/`. Поставщик видит свою партию и общее мероприятие схемы, если в нём нет услуг или есть хотя бы одна его услуга. Партия другого поставщика с тем же видом ему не видна. Число ЛС в партии считается только по счетам, которые пользователь и так видит. Просмотр реестра и матрицы пишется в аудит одной записью. Открытие списка добирает счёт без мероприятия и повторяет сорвавшийся обзвон. Открытый автообзвон — текущий шаг цепочки, сценарий его заново не запускает, матрица его не запускает вовсе: иначе каждая страница реестра ждёт пересчёт всех таких счетов. У партии в ответе есть `progress` — сколько частных мероприятий видно пользователю (`total`) и сколько из них завершено (`done`).
- Карточка партии (`/measures/{id}`): слева вид, шаблон или канал, даты, окно обзвона и следующее действие, справа — сколько ЛС завершено с полосой прогресса. Ниже прокручиваемый список лицевых счетов, которым назначено это мероприятие: у ручного запуска это счета одной записи, у сценария — все счета того же шага и шаблона. Под списком журнал переходов: когда, кто, было → стало, основание. Колонки списка зависят от вида: у обзвона телефон и результат, у уведомления адресат и время отправки, у предупреждения способ вручения и статус отправления, у отключения даты приостановления и возобновления. Блоки действий появляются только когда они применимы: согласование видит локальный администратор, «Принять задание» — специалист поставщика, отмена исчезает, как только услуга приостановлена. Строка открывает форму результата прямо в таблице. Если статус пришёл от заглушки AMI, под ним написано «Внешний вызов не выполнялся», исходящий номер, длительность и доля прослушивания. Если письмо пришло от заглушки SMTP, под временем отправки написано «Письмо не отправлялось». Переход между карточками перечитывает партию по смене id, а не только при первом открытии.
- Третий вид реестра — «Готовы к отключению» (иконка `power_off`): лицевые счета с истёкшим сроком предупреждения, непогашенным долгом и услугами, которые можно отключать. Отметка счёта включает все его услуги, отдельные услуги снимаются флажками. Кнопка создаёт партию отключения и открывает её карточку. В списке партий у строки видно, сколько ЛС уже завершено, а название ведёт в карточку. На вкладке «Мероприятия» карточки ЛС рядом со статусом партии показывается статус по этому лицевому счёту.
- Частное мероприятие (`MeasureItem`): по одной записи на каждый ЛС партии, со своим статусом (назначено, выполняется, завершено, прервано пользователем, завершено с ошибкой), телефоном или адресатом, результатом и примечанием. Статус партии пересчитывается по частным записям; пауза по наследственному делу пересчётом не снимается. Каждый переход пишется в `MeasureEvent` (кто, было, стало, основание). Состав мероприятия отдаёт `GET /api/v1/measures/{id}/` (`items`, `campaign_total`) — счета этого шага и шаблона внутри контура, не больше 300 строк.
- Мероприятие вне сценария (`POST /api/v1/measures/`) запускают локальный администратор и суперадминистратор. Специалист внутри мероприятия заводит задания: `POST /api/v1/measures/{id}/tasks/`, `POST .../task-status/`. На карточке партии и на вкладке «Мероприятия» лицевого счёта один и тот же блок: название, статус «Открыто» или «Выполнено», срок и кнопка смены статуса. Галочек у задания нет: отметка пункта не двигает мероприятие и не блокирует этап. Четыре пункта пакета исполнительной надписи на лицевом счёте остаются отдельным чек-листом. У остальных этапов с действиями на вкладке «Активности» тоже чек-лист: направление нотариусу, иск, решение суда, направление в ОПИ, меры ОПИ, невозможность взыскания и списание. Обязательный пункт подсвечен, пока не закрыт; пункт «по данным дела» система закрывает сама. Вкладка «ОПИ» дела повторяет этот список слева, пустые обязательные поля выделены. «Направлено в ОПИ» ждёт орган, дату направления и исполнительный документ; если номер производства уже пришёл из АИС ПРИС, переход идёт по нему. «Меры ОПИ приняты» ждут меру или сведения о мерах из ПРИС. Акт о невозможности взыскания на вкладке ОПИ не обязателен: взыскание идёт по исполнительному документу, акт прикладывают, если взыскать не удалось. Переход в «Невозможность взыскания» требует такой акт, списание — три акта и согласие маршрута. Колонка чек-листа называется «Переход». Она есть у каждого пункта этапа и открывает то место, где пункт заполняют: пакет исполнительной надписи — вкладка дела «Комплект», нотариат и отказ — «Нотариус», иск и решение суда — «Суд», направление в ОПИ, меры, акты и взыскание — «ОПИ», списание — «Списание». Обзвон, уведомление и отключение открывают карточку самого мероприятия. Вкладка «Мероприятия» лицевого счёта этим переходом не открывается. Колонка претензионно-исковой работы совпадает с этапом карточки: если дело ещё не заведено, карточка всё равно стоит в колонке этого этапа, а при открытии дело создаётся на нём же. Название мероприятия взыскания на вкладке «Мероприятия» берётся из того же этапа. Отбор при запуске принимает услуги первичными ключами строк (`service_ids`) или кодами услуг АИС (`catalog_service_ids`): второе раскрывается в строки на уже отобранных счетах внутри контура. Ответ 201 и поле `skipped`: по каждому непрошедшему ЛС — номер и причина. Обзвон берёт номер как есть, если он уже начинается с +375. Иначе код +375 дописывается в начало (в том числе к короткому номеру из выгрузки вроде 1111111); номер, который уже начинается с другого плюса, в обзвон не попадает. Юридические лица участвуют по флагу `call_legal`; диапазон `group_from`–`group_to` режет по группе долга. Уведомление принимает только `email` или `sms` и требует адресата (мессенджеры на этом этапе не подключаются). По всем видам, кроме передачи взыскания, ЛС с открытым наследственным делом пропускается. Если не прошёл ни один ЛС — 400 с тем же `skipped`. В плашке ошибки одинаковые причины схлопываются в счётчик, например «Нет номера +375 (27)».
- Прогон автообзвона — «Назначить» в реестре ЛС только создаёт мероприятие. Ручной запуск — кнопка «Провести» над списком реестра мероприятий (`POST /api/v1/measures/conduct/`). Пока ни одна строка не отмечена, кнопка неактивна. Список под ней прокручивается, кнопка остаётся на месте. Её видят специалист, локальный администратор и суперадминистратор начисляющей организации. Сценарий этой кнопкой не стартует и идёт по расписанию. Уведомление из той же отметки ставится в отправку. Предупреждение, отключение и взыскание отмечаются на карточке. Вне окна строка не пишется, ответ называет окно. `python manage.py dial_calls` из `app/backend` остаётся для повторов по расписанию. Для стенда до 27-го числа: `--at ГГГГ-ММ-ДДTЧЧ:ММ`. Команда берёт открытые партии, если момент внутри окна сценария и не раньше `call_from_day` (по умолчанию 27, не 26-е). Будни по умолчанию 18:00–21:00, выходные 10:00–22:00; окно лежит на сценарии, автозапуск больше не подставляет 09:00–18:00. Номер выбирается заново: только +375, городской или мобильный по правилу дня. Юридическое лицо пропускается, пока у схемы выключен «звонить юридическим лицам». Наследственное дело строку не заполняет. Частота читается из шага сценария: группы 1–2 каждый день, один дозвон закрывает повтор; группа 3 — раз в 3 дня, число в шаге меняется; группы 4–6 один раз. Исходящие номера схемы (`outgoing_numbers`) крутятся и уходят в адаптер. Запись разговора и перевод на оператора через `PATCH /api/v1/nsi/scenarios/calling/` не включаются. Голосовой шлюз отвечает в том же вызове: `GET /gw/v1/voice/status` (режим, без набора), `POST /gw/v1/voice/dial` (один номер) и `POST /gw/v1/voice/batch` (до 30 номеров, общий текст или ролик). По умолчанию `GW_VOICE_MODE=stub`: набор не выполняется, хвост номера задаёт исход (`00` неверный, `01` занято, `02` недозвон, иначе дозвон 36 с и 72 %), идентификатор `voice-…`, `external_call=false`. `GW_VOICE_MODE=ami` делает Login и Originate в Asterisk. Номер не из +375 на станцию не уходит. Диалплан заказчика читает `ERIP_TEXT`, `ERIP_AUDIO`, `ERIP_RECORD`, `ERIP_TRANSFER`; шаблон канала — `GW_AMI_CHANNEL` с `{phone}` или `{digits}`. Обратно приходят статус, длительность и, если станция прислала `UserEvent`, доля прослушивания и ссылка на запись (`recording_ref`, файл в ПМ не хранится). Пока AMI не ответил, строка партии не закрывается. В карточке партии у заглушки написано «Внешний вызов не выполнялся»; у боевого вызова — исход и запись, если она есть. Повтор в тот же вечер вторую строку не создаёт. Ручной `POST .../result/` пишет те же поля в ту же строку и фразу про заглушку не ставит. CSV партии по-прежнему собирается. Коллекция запросов — `postman/collections/Телефония AMI`, окружение — `postman/environments/Локальный шлюз.environment.yaml`. Прогон из корня репозитория: `postman collection run "postman/collections/Телефония AMI" -e "postman/environments/Локальный шлюз.environment.yaml"`. При `ami` эти запросы звонят на указанные номера; для проверки конверта оставьте `stub`. Nginx на `/gw/` ждёт ответ 120 с. Поля окна, исходящих номеров и результата звонка добавляют миграции `users.0006`, `nsi.0013`, `debts.0026` и `debts.0029` (ссылка на запись, файл в ПМ не хранится). `POST .../send/` ставит письма и SMS в оповещения. Повтор той же строки, пока письмо в очереди или уже доставлено, второе письмо не создаёт. Ошибка доставки переносится в частное мероприятие со статусом «Завершено с ошибкой». Отправитель, имя, запасная тема и подпись схемы — `GET/PATCH /api/v1/nsi/scenarios/mail/` (локальный администратор и суперадминистратор своей схемы), на подвкладке шага «E-mail». Тема шаблона, если она заполнена, важнее темы схемы. Сумма, ФИО и адрес в письме берутся из лицевого счёта. Прочтение не отмечается. Пока `GW_EMAIL_MODE=stub`, письмо не уходит, в строке `external_call=false`. `GW_EMAIL_MODE=smtp` отправляет через SMTP заказчика (`GW_SMTP_HOST`, порт 587 и STARTTLS либо `GW_SMTP_SSL` для 465). Пустой адрес отправителя схемы боевой режим не принимает. Отказ сервера по адресу — недоставка. Позднее уведомление о недоставке из ящика возвратов не читается. `GET /gw/v1/email/status` показывает режим и не отправляет письмо. Поля отправителя добавляет миграция `users.0008`. `POST .../deliver/` проставляет вручение предупреждения (способ, дата, ФИО получившего либо акт об отказе).
- Отключение: вручение предупреждения задаёт срок оплаты (свой у схемы, иначе общее `warning_wait_days`, по умолчанию 5 дней). До истечения срока отключение не запускается — нужна записанная причина в `override_reason`. `GET /api/v1/measures/ready-to-disconnect/` показывает ЛС с истёкшим сроком, непогашенным долгом и услугами, которые вообще можно отключать. Если в справочнике включено `disconnect_requires_approval`, список уходит локальному администратору: `POST .../approve/` или `.../reject/` с причиной. Согласованное задание падает во входящие специалистам поставщика. `POST .../accept/` принимает только пользователь контура поставщика и двигает этап воронки. `POST .../confirm/` с `action` = `suspend` или `resume` и `source` = `pm` или `ais` фиксирует факт. `POST .../cancel/` с причиной отменяет задание, пока поставщик не приостановил услугу; после приостановления отмена запрещена.
- Оплата не включает услугу обратно сама: погашение закрывает открытые частные мероприятия, а уже приостановленное отключение оставляет и кладёт закреплённому специалисту задание проверить возобновление.

### Оповещения

1. Каркас выбирается по группе долга ЛС (`effective_group`: ручная, иначе расчётная) и каналу: локальный шаблон схемы, иначе центральный из фикстуры `message_templates` (группы 1–6, канал e-mail). `POST /api/v1/notifications/` может не передавать `template` — тогда каркас подставится сам. В контекст попадают `{fio}`, `{account}`, `{amount}`, `{address}`, `{debt_group}`, `{group_name}` — эти ключи берутся только из лицевого счёта, поля из запроса их не затирают. Название группы отдаёт карточка ЛС (`group_name`). Каркас группы подставляется при отправке уведомления из реестра: сначала шаблон с названием партии, иначе каркас группы. Повтор с тем же автором, ЛС, шаблоном и каналом, пока статус `new` или `queued`, возвращает уже созданное оповещение и в шлюз не уходит. Повтор `POST /api/v1/measures/{id}/send/` для той же строки тоже не создаёт второе письмо. `POST .../resend/` в статусах `new` и `queued` отвечает 400. Приветствие шлюз добавляет отдельно. Подпись берётся из схемы (`mail_signature`), пустая подпись остаётся «С уважением, ЖКУ». В `meta` уходят `mail_from` и `mail_from_name`, если они заданы. `POST .../mark-read/` для канала e-mail отвечает 400: прочтение письма не отмечается. Отдельного экрана правки писем нет: текст берётся из фикстуры `message_templates`. `POST /api/v1/templates/{id}/restore/` по-прежнему возвращает шаблон из архива.
2. `NotificationDispatcher` (зависит от абстракции `GatewayClient`) → `HttpGatewayClient` асинхронно через `httpx.AsyncClient` → `POST /gw/v1/notifications` с заголовком `X-Internal-Token` (ответ 202). Адрес callback шлюз собирает сам из `GW_BACKEND_URL` и id оповещения, поле из запроса не принимается.
3. Шлюз пишет `delivery_log`, в фоне формирует текст декоратором `@with_greeting` («Добрый день, {имя}! …» и подпись схемы либо «С уважением, ЖКУ») и передаёт его адаптеру канала из `AdapterRegistry`. `inbox` и `sms` остаются заглушками. `email` при `GW_EMAIL_MODE=stub` письмо не отправляет (`external_call=false`), при `smtp` ходит в SMTP. `voice` зависит от `GW_VOICE_MODE`. В шаблоне подставляются только простые имена `{fio}`, `{account}` и т.п. Заголовок подтверждения прочтения не ставится.
4. Итог шлюз возвращает в backend: `POST /api/v1/notifications/{id}/delivery-status/` с заголовком `X-Internal-Token` (до трёх попыток). В теле ещё `provider_message_id` и `external_call`. Статус становится `sent` или `failed` и тем же вызовом переносится в частное мероприятие, если письмо или SMS поставило уведомление из реестра мероприятий: ошибка доставки видна в строке ЛС. У заглушки в журнале строки написано «Письмо не отправлялось». Перед отправкой строка журнала атомарно переводится из `accepted` в `processing`, поэтому два процесса uvicorn не отправляют одно сообщение дважды. Зависшую доставку (дольше 2 минут) шлюз забирает снова при старте. Завершённые записи `delivery_log` старше `GW_LOG_RETENTION_DAYS` (по умолчанию 90) удаляются при старте.
5. `context: {"_fail": true}` имитирует отказ канала. Ошибка попадает в `ErrorLog` с тем же `X-Request-ID`, что у исходного запроса.

### Границы модулей

Приложения Django — будущие сервисы. Сейчас они в одном процессе и одной базе, HTTP-границы уже разделены.

| Контекст | Где | Что выносить первым |
|---|---|---|
| Пользователи и доступ | `apps/users`, `AccessScope` | Проверка контура и списка организаций |
| Реестр задолженностей | `apps/debts/views.py` вызывает `apps/debts/services/` | Группа, рейтинг, наследство, реестр договоров (`services/contracts.py`) |
| Загрузка АИС | `apps/imports` | Пакетный приём файла; пересчёт вызывает сервисы реестра, не представления |
| Справочники | `apps/nsi` | Шкалы, сценарии, параметры расчёта |
| Оповещения | `apps/notifications` | Уже ходит в шлюз по HTTP |
| Шлюз доставки | `app/gateway` | Уже отдельный процесс |

Представление не содержит правила должника и поставщика: оно проверяет запрос и вызывает функцию сервиса. Другой контекст не импортирует `views`. Общая база — временная связка; замена её на вызов сервиса не должна трогать шаблоны Angular.

### Паттерны

| Паттерн | Где |
|---|---|
| Singleton | `gateway/app/core/singletons.py` (`Database` — пул `AsyncEngine`, `HttpClient` — общий `httpx.AsyncClient`), `get_gateway_client()` в Django. Соединениями Django с БД управляет ORM (`CONN_MAX_AGE`) |
| Decorator | `@with_greeting`, `@api_response` (конверт `{"data", "meta": {"request_id", "duration_ms"}}`) |
| Strategy / Adapter | `ChannelAdapter` + `AdapterRegistry`; `PrisClient` / `BnpClient` со Stub- и Http-реализациями |
| Repository | `apps/debts/repositories.py` |
| DIP / OCP | Dispatcher зависит от `GatewayClient`; новый канал — новый класс и `registry.register(...)` |

### Интеграции («Информация по интеграции»)

- **ПРИС:** схемы запросов и ответов по регламенту (`PutClaimantSaveDataDebt`, `PutClaimantSaveDataDebtWOFE`, `PutClaimantSaveRepayDebt`, `GetClaimantInfoBy*`, `GetNSIData`). Авторизация `x-user_id` / `x-accesskey` → `x-token` + `x-timestamp`, кэш токена (память или Redis) на 30 минут; перед новым токеном шлюз вызывает `logout`. Пустой `p_proc_num` в запрос сведений не попадает. Ответ с `code` «1» и `processStatus` кроме 1000 и 1001 считается отказом. `GW_PRIS_MODE=stub` (по умолчанию) пакет проверяет и не отправляет. `channel` — тестовый канал: тот же `HttpPrisClient` ходит во встроенный стенд шлюза, номер производства начинается с `CH-`, справочник 120 остаётся примером регламента, контур Минюста не вызывается. Логин и ключ стенда по умолчанию `channel` / `channel`. `http` вызывает контур Минюста по `GW_PRIS_BASE_URL` (в регламенте тестовый адрес `http://192.168.101.81:10116`; боевой адрес Минюст ещё не выдал). itVPN поднимает заказчик на сервере, шлюз идёт его маршрутом. `GET /gw/v1/integrations/pris/status` в этом режиме проверяет порт (`tunnel`) и пакет не шлёт. Нужны `GW_PRIS_USER_ID` и `GW_PRIS_ACCESS_KEY`. Карточка дела собирает пакет 3.11.02 из регистрации, дерева адреса, реквизитов организации и файлов; коды справочников без значения в ПРИС не подставляются. В `stub` и `channel` тот же адрес канал не трогает. `GET /gw/v1/integrations/pris/nsi` и `GET /api/v1/claims/pris-dictionaries/` отдают справочники: в `stub` и `channel` это сокращённый пример регламента (справочник 120), при `http` — ответ Минюста. Журнал обмена пишется в дело без тел файлов. Ход производства (остаток, статус, меры, начисления, погашения) сохраняется при `http` и при `channel`. В режиме `channel` на деле пишется `opi_mode=channel`. `python manage.py refresh_pris` из `app/backend` обновляет уже переданные дела.
- **БНП:** манифест заявления (`BnpManifest`) с проверками:
  - `personType` и условно обязательные поля;
  - структура личного номера (14 символов) и УНП;
  - `amount` в формате `10.00`, даты в формате `YYYY-MM-DD`;
  - `serviceId`, `typeId` и `docType` — по справочникам БНП;
  - документ — `.pdf` не более 15 МБ; ЭЦП в пакете — отдельный файл `.pdf.sgn` или `.pdf.p7s` (`signatureName`).

  Справочники извлекаются из `Справочники БНП.docx` скриптом `scripts/extract_bnp_dictionaries.py`. Список нотариальных контор — снимок страницы https://belnotary.by/nayti-notariusa/notarialnye-kontory-i-notarialnye-byuro/, его обновляет `scripts/extract_notary_offices.py`. Рабочая карта кабинета, манифеста и услуг ЖКУ — `docs/tz/BNP_INTEGRATION.md`.
- Проверочные эндпоинты: `/gw/v1/integrations/pris/status`, `/pris/echo`, `/pris/claimant-info`, `/pris/save-data-debt/validate`, `/bnp/validate`, `/bnp/dictionaries`. `pris/status` пакет не отправляет; в режиме `http` проверяет, открыт ли порт контура.

### Логи и ошибки

- JSON-логи в stdout (поля `timestamp`, `level`, `service`, `request_id`, `user_id`, `path`, `message`), формат готов к ELK/OpenSearch.
- Необработанные ошибки backend и ошибки шлюза пишутся в `ErrorLog`: `/api/v1/audit/errors/` и раздел «Журнал ошибок», доступны только суперадминистратору.
- Просмотр карточки ЛС и изменения записываются в `AuditLog`. Список и поиск лицевых счетов и регистраций пишут одну строку на запрос (фильтры и страница), а не строку на каждую запись. В списке регистраций идентификационный номер маскируется, в карточке ЛС он полный. IP в журнале — адрес, который NGINX дописал в `X-Forwarded-For` (`NUM_PROXIES=1`).

### Роли (MVP)

- `superadmin` — все схемы.
- `local_admin` — своя схема: специалисты и наблюдатели, шаблоны, импорт. Другого локального администратора и суперадмина он не видит и не назначает.
- `specialist` — реестр, карточки, оповещения.
- `contour=supplier` — пользователь видит только услуги, где его организация назначена поставщиком (`AccountService.provider_id`), и лицевые счета, на которых такие услуги есть. Пустой список организаций поставщика даёт пустой реестр. Суммы долга на карточке и в группировке — только его услуги. Группа, название группы, сценарий, этап воронки, рейтинг, месяцы долга и дата возникновения на карточке и в списке ЛС тоже считаются по его услугам с остатком, а не по старшей группе всего счёта. По умолчанию контур `billing`: видимость по обслуживающей организации лицевого счёта.
- `observer` — только чтение.

### Взыскание и сценарии (показ заказчику)

Разделы открываются из левого меню, в том числе «Настройка». Реестр лицевых счетов в списке и группировке занимает окно до низа страницы и прокручивается внутри. На грид-доске правый край заголовка сужает и растягивает один столбец, соседние свою ширину не отдают. Так устроены список и группировка реестра ЛС, срезы «Поставщики», «Лица» и «Услуги» и группировка договоров, список, матрица и список «к отключению» мероприятий, список претензионно-исковой работы, таблицы вкладок карточки ЛС, мероприятия на карточке договора, счета и журнал на карточке мероприятия, журнал ошибок, оповещения, очередь и журнал загрузки, пользователи организации, шаги сценария и таблицы рейтинга. Ширина хранится у учётной записи (`GET/PUT /api/v1/board-widths/{board}/`), другой пользователь её не видит. Набор столбцов реестра и вкладок «Регистрация», «Услуги» и «Оплата» открывается кнопкой «Столбцы» выпадающим списком и тоже остаётся у этой учётки. Список и группировка с теми же столбцами делят одну ширину этого пользователя. Остальные списки дел, договоров и таблицы на карточках лежат в окне высотой не больше десяти строк: колесо прокручивает это окно, страница от длины списка не растёт. Список мероприятий и матрица под ним идут одним полотном и прокручиваются вместе со страницей. На этом реестре переключатель видов — значки канбана, списка, календаря и графика, как на макете. Под окном остаётся переключатель страниц, где он уже был. На мероприятиях и в претензионно-исковой работе тот же фильтр, что на реестре ЛС: поиск, группа, рейтинг, этап, избранное и окно своего фильтра. У мероприятий ещё месяц, вид и группировка загруженных строк по статусу, виду или исполнителю. Календарь всех реестров — сетка месяца с плашками «вид — должник»: цвет по группе задолженности счёта (1 зелёный, 2 синий, 3 жёлтый, 4 красный, 5 оранжевый, 6 тёмный). Справа три карточки: группы и число событий, типы с галочками, подсказка. Шапка: назад и вперёд, «Сегодня», «месяц год — мероприятия по делам», день/неделя/месяц. Щелчок по группе в легенде включает тот же фильтр, что поиск реестра. Такая же сетка, шапка и три карточки стоят на реестре лицевых счетов, реестре договоров и в претензионно-исковой работе. На реестре ЛС, реестре договоров, мероприятиях и претензионно-исковой работе один и тот же переключатель: список, канбан, календарь и «Граф. аналитика». Меняется состав, картинка та же. На договорах в списке остаются срезы «Лица» и «Услуги», на мероприятиях рядом — скачивание списка и «к отключению». Графики: `GET /api/v1/accounts/charts/?scope=` пустой — все ЛС контура, `measures` — ЛС с мероприятиями, `claims` — группа 3 и старше, открытое дело, этап надписи или ОПИ, либо мероприятие «взыскание», `contracts` — ЛС с услугами. Претензионно-исковая работа показывает должников с группы 3, с мероприятием «взыскание» или с открытым делом. Список, канбан, календарь и графики берут одну выборку (`scope=claims` на `GET /api/v1/accounts/`, `.../kanban/` и `.../calendar/`). Канбан этого раздела — пять колонок по 2–3 этапа: пакет (очередь, подготовка, нотариус), ответ нотариуса, суд, ОПИ и итог. Карточка та же, что в реестре лицевых счетов, на ней строкой написан точный этап. Перенос левой кнопкой ставит дело на входной этап колонки, значок выбирает точный этап. Обязательный шаг без даты вручения, тарифа или записанной причины не проходит. В списке без открытой карточки — таблица этих должников. Открытое дело занимает всю ширину раздела, колонки должников рядом с карточкой нет; назад ведёт «К списку». Кнопка-сетка слева от «ЕРИП · Работа с задолженностью» сворачивает левое меню до иконок: название пункта — во всплывающей подсказке. `GET /api/v1/claims/` по-прежнему отдаёт дела и очередь `assigned`. «Добавить исполнительную надпись» открывает окно создания периода. Лицевой счёт ищется с двух символов, список не длиннее 12 строк и закрыт, пока поле не нажато. Дальше те же поля, что раньше стояли на вкладке карточки ЛС: период с и по, дата вручения или акт о невручении, дни на погашение, нотариальная контора, долг, пеня и ФИО за период из АИС. «Сохранить и открыть пакет документов» создаёт отдельное дело за этот период (`POST /api/v1/accounts/{id}/writ-draft/`). Группа 3 для этой кнопки не требуется: нужны два предъявленных месяца, дата вручения или акт и период без пересечения с уже созданной надписью. Вкладка «Исполнительная надпись» на карточке ЛС форму не показывает: там список пакетов и кнопка «Перейти в пакет». У группы 4 и старше на карточке видна ветвь выселения и отчуждения. Дело ведёт лицевой счёт: дата вручения предупреждения и нотариальный тариф обязательны для статуса «Направлено нотариусу». Отказ нотариуса открывает иск и записывается только с комментарием или с постановлением об отказе на карточке счёта. Другой файл счёта отказ не проводит. Комплект надписи показывает эти файлы: расчёт, доверенность, скан. Поля выселения и даты пакета видны, когда вид иска — выселение или отчуждение. «Невозможность взыскания» требует акт ОПИ, списание — три акта и согласие всех выбранных согласующих. Отказ одного акт не формирует. Статус «Взыскано» включается после отметки, что выгрузка АИС принесла погашение долга, пени и тарифа; само сальдо при этом не переписывается.

Пакет для личного кабинета БНП собирается на карточке дела. Состав — `POST /api/v1/claims/{id}/package/`: услуга из справочника (для ЖКУ отмечены 571, 572 и 576, пункт выбирает пользователь), должники, строки задолженности. Сумма основного долга — сумма колонки услуг «Исходящее сальдо с пенями», та же, что «Сумма основного долга» на карточке. Если услуг на счёте нет, берётся исходящее сальдо карточки. Пеня — сумма «Исходящее сальдо пени» по услугам. Введённую сумму сервер не принимает. Заявление PDF — `POST .../package/application/`. Остальные PDF и файл ЭЦП `.pdf.sgn` или `.pdf.p7s` — `POST .../package/documents/` (не больше 15 МБ, подпись отдельным файлом). Обязательны заявление, расчёт и доверенность. `POST .../package/form/` записывает манифест. Скачивание: `GET .../package/manifest/`, `GET .../package/archive/` и `GET .../package/documents/{id}/pdf|signature/`. На комплекте поле «E-mail для уведомлений нотариуса»: один адрес или несколько через запятую. Это адрес для кабинета БНП, контакт должника туда не подставляется. «Подпись в Internet Explorer» (`POST .../ie-sign-ticket/`) копирует ссылку на статическую страницу `/ie-sign/?t=…` (без Angular): в IE кнопка «Подписать документы AvPass» открывает диалог АВЕСТ (сертификат/пароль), `GET/POST /api/v1/ie-sign/<token>/…` сохраняет отсоединённый PKCS#7. Ticket 20 минут. В диагностике страницы — метка сборки `20261030c` (иначе IE кэширует старый JS). Angular-карточка в IE не открывается. Кнопки «Подписать документы заявителя» / «Подписать доверенность» (`POST .../sign-documents/`) по-прежнему зовут плагин в текущем браузере (в Chrome не загрузится). Сертификат — РУЦ ГосСУОК, ключ AvPass. «Собрать архив» пишет zip, «Отправить» неактивна. Дистрибутив — https://nces.by/pki/info/software. Кнопка «Направить нотариусу» после собранного пакета и приложенных файлов ЭЦП возвращает номер `stub-…` и прямо пишет, что в личный кабинет БНП пакет не уходил. «Подписать PDF ключом AvPass» в блоке ПРИС подписывает выбранное вложение тем же плагином и кладёт `.p7s` в файлы счёта. Если PDF выбран «из пакета», ПРИС берёт подпись комплекта. Когда лицевой счёт доходит до шага «Исполнительная надпись», открывается дело и то же мероприятие взыскания; печатные формы этого шага попадают в комплект. «Передать в ПРИС» собирает пакет 3.11.02 (для файла `.sgn` — сервис WOFE). «Сохранить черновик» пишет реквизиты, не вызывая ПРИС. Подпись принимается только как отдельный `.p7s` или `.sgn`; локальная отметка пакета БНП отклоняется. При `GW_PRIS_MODE=stub` карточка пишет, что пакет проверен и в АИС ПРИС не уходил; номер из примера регламента и ответ о ходе на дело не записываются. При `GW_PRIS_MODE=http` код 1000 или 1001 сохраняет `responseId`, «Обновить ход производства» вызывает 3.11.04 или 3.11.05, записывает остаток, статус, меры, начисления и погашения и переводит дело в «Направлено в ОПИ», когда пришёл номер производства, а при мерах — дальше. «Передать погашения» отправляет 3.11.03. Журнал последних обменов виден в блоке «Передача в ПРИС». Ручная запись статуса ОПИ сервисы не вызывает. Реквизиты взыскателя лежат в `Organization.pris_claimant` и правятся на «Организации и пользователи» (`GET/PATCH /api/v1/organizations/{id}/pris-claimant/`, локальный администратор своей схемы и суперадминистратор) и из дела. Коды справочников — в `ClaimCase.pris_request`, список для полей — `GET /api/v1/claims/pris-dictionaries/`. `python manage.py refresh_pris` обновляет ход по делам с идентификатором долга или номером производства. Итог списания помечает, что файл в АИС ещё не выгружен.

«Настройка» в левом меню состоит из четырёх разделов. «Правила рейтинга и групп» показывает шкалу 1–6, базовый сценарий группы и пороги рейтинга A–E. Сохраняет суперадминистратор: границы `PUT /api/v1/nsi/debt-groups/replace/`, названия сценариев `PATCH /api/v1/nsi/scenario-rules/{id}/`, пороги `PATCH /api/v1/nsi/calculation-settings/current/`. История рейтинга при сохранении не переписывается; галка применяет новые пороги к текущим буквам. Отягчающие признаки буквы D — «не занят в экономике» и банкротство или ликвидация. «Организации и пользователи» (`GET /api/v1/organizations/` отдаёт число пользователей, число ЛС и имя локального администратора, `GET/POST/PATCH /api/v1/users/`): слева схемы, справа пользователи выбранной схемы. Кнопка «Изменить» у строки пишет `PATCH /api/v1/users/{id}/`: фамилия, имя, отчество, логин, e-mail, телефон, должность, роль, признак согласования и контур. Новый пароль необязателен: пустое поле оставляет прежний. Смена роли со специалиста снимает согласование и ставит контур начисляющей организации. У специалиста есть признак `can_approve`: с ним он пропускает шаг сценария и этап воронки. Блокировка снимает с человека открытые мероприятия, задания и закреплённые счета и передаёт их активному специалисту или локальному администратору той же схемы и того же контура. «Сценарии и шаблоны» — на подвкладке «Сценарий» список и порядок шагов. Условия шага (группы, категория, тип организации, ФЛ/ЮЛ, телефон, оплата, предыдущий шаг, действие и переход) открываются на подвкладке этой меры, например «Автообзвон». Окно обзвона и общее правило мобильного номера — на той же подвкладке; исходящие номера и признак ЮЛ схемы — во вкладке «Интеграции → Asterisk AMI». Сроки схемы задаются на подвкладке сценария. Назначение опубликованного сценария запускает первый подходящий шаг и пишет на мероприятии версию сценария. Пауза хранит историю и причину. Центральный «Стандартное взыскание» копируется в схему. Публикация поднимает версию. Без галки «Перевести уже запущенные счета» назначенный лицевой счёт остаётся на своей версии. Шаг «мессенджер» сохраняется и не отправляет сообщение. На шаге «Исполнительная надпись» задаётся чек-лист: название, порядок, критерий приёмки и признак «обязателен» или «можно пропустить». Дата вручения, срок добровольной оплаты, пакет и нотариальный тариф из чек-листа не убираются. Пропуск необязательного этапа, например отключения, при направлении нотариусу записывается с причиной. Карточка дела показывает чек-лист сценария, назначенного на счёт; без сценария берётся тот же законный набор. Печатная форма — лист A4: поля с подчёркиванием, таблица с рамкой и блок подписи. Порядок блоков, шрифт и выравнивание задаются на макете. PDF одного документа собирает WeasyPrint по этому листу (без библиотеки — прежний сборщик). Пакет до 100 счетов по-прежнему один файл; адресат — должник, поставщик или администрация района. Файл остаётся на версии макета. Экрана «Шаблоны сообщений» нет. Откат версии шаблона письма по API создаёт новый номер, уже отправленное оповещение помнит старый. Шаг сценария хранит идентификатор шаблона: переименование не отвязывает шаг. Старый шаг без идентификатора остаётся на записанном имени. Признак «звонить юридическим лицам» задаётся на схеме (вкладка Asterisk) и, отдельно, на сценарии. Общее правило мобильного номера суперадминистратор сохраняет в разделе «Сценарии и шаблоны». «Интеграции» — единый экран каналов: SMTP (почта схемы `GET/PATCH /api/v1/nsi/scenarios/mail/` и статус шлюза), Asterisk AMI (номера схемы `…/calling/` и статус AMI), SMS, мессенджеры, Белпочта, АИС ПРИС, ЛК БНП, АИС «Расчет-ЖКУ». Список и статус — `GET /api/v1/integrations/`. Секреты `GW_*` из браузера не правятся.

Канбан и список «Взыскания» берут адрес, группу, рейтинг, пеню и специалиста с лицевого счёта. Чтобы окна не были пустыми, по свободным счетам раскладывается выборка:

```powershell
cd E:\erip-main\app\backend
$env:POSTGRES_HOST=''
E:\erip-main\app\.venv\Scripts\python.exe manage.py seed_claim_sample
```

Команда открывает до восьми дел на разных этапах, центральный сценарий и макет предупреждения. Уже открытые вручную дела она не переписывает. Для Docker ту же команду запускают внутри контейнера backend после `docker compose up --build -d`.

«Граф. аналитика» на этих разделах открывает одни и те же три вида: столбцы по этапам воронки (тёмная часть — основной долг `balance_out`, светлая — пеня `balance_mulct_out`), две круговые доли дел и суммы по группам 1–6, линия динамики по месяцам. Подпись над графиком называет раздел. Группа на круговой — действующая группа лицевого счёта (ручная, если задана). `GET /api/v1/accounts/charts/` режется тем же контуром, что реестр, и параметром `scope`, как в абзаце выше: поставщик суммирует только свои услуги. Месяцы — последние 12 срезов `BalanceHistory`; если истории нет, на линии одна точка текущего среза (`months_source`: `history` или `current`). Просмотр пишет одну строку аудита. Кнопка «Экспорт CSV» собирает файл в браузере из уже загруженной сводки. На реестре ЛС у переключателя есть ещё карта.

- `GET /api/v1/accounts/charts/`
- `GET/POST /api/v1/claims/`, карточка `GET/PATCH /api/v1/claims/{id}/`
- `POST /api/v1/claims/{id}/package/`, `.../package/application/`, `.../package/documents/`, `.../package/form/`, `.../sign-and-send/`; `GET .../package/manifest/`, `GET .../package/archive/`, `GET .../package/documents/{id}/pdf|signature/`; `DELETE .../package/documents/{id}/`
- `POST .../send-notary/`, `.../notary-result/`, `.../acts/` (`DELETE .../acts/{act_id}/`), `.../opi/`, `.../opi-measures/` (`DELETE .../opi-measures/{measure_id}/`), `.../pris/autofill/`, `.../pris/draft/`, `.../pris/submit/`, `.../pris/refresh/`, `.../pris/repay/`, `GET /api/v1/claims/pris-dictionaries/`, `GET /api/v1/claims/pris-status/`, `.../ais-receipt/`, `.../writeoff/`, `.../decide/`, `.../move/`
- `GET/POST/PATCH/DELETE /api/v1/nsi/opi-offices/`, `GET/PATCH /api/v1/organizations/{id}/pris-claimant/`, `python manage.py refresh_pris`
- `GET/POST /api/v1/nsi/scenarios/`, `POST .../copy/`, `.../publish/` (`apply_to_running`), `.../restore/`, `.../assign/`, `GET/PATCH .../calling/`
- `GET/POST /api/v1/nsi/print-forms/`, `POST .../render/` (`account` или `accounts`, до 100), `GET .../documents/{id}/`, `GET .../package/{batch}/`, `POST .../restore/`
- `PUT /api/v1/nsi/debt-groups/replace/`, `PATCH /api/v1/nsi/calculation-settings/current/` (`apply_recorded`), `POST /api/v1/templates/{id}/rollback/`

Контур доступа реализован в одном месте, `apps/users/scoping.py`, и действует и для списков, и для запросов по id. Оповещение по лицевому счёту дополнительно ограничено назначенными обслуживающими организациями. «Прочитано» ставит только получатель.

На экране входа только логин и пароль. Учётные записи для проверки ролей создаются при старте backend: `a.poleshchuk@raschet.by` и `a.galdytskaya@raschet.by` с паролем `Raschet-Test-2026`, `roman123` и `andrei123` с паролем `1234567890`. Повтор старта пароль возвращает. После верного пароля сессия ещё не открыта: экран показывает роли (суперадминистратор, локальный администратор, специалист, наблюдатель, поставщик, Тест ЖЭС). `POST /api/v1/auth/role-choice/` записывает выбранную роль на эту учётную запись и только тогда выдаёт токен. Обычный логин этот шаг не проходит. Специалист, локальный администратор, наблюдатель и поставщик привязываются к схеме, в которой больше всего лицевых счетов; поставщик дополнительно ограничивается организациями с признаком поставщика. «Тест ЖЭС» — тот же контур поставщика, но одна организация: поставщик с наибольшим числом услуг. В шапке у поставщика с одной организацией показано её краткое имя, рядом — имя пользователя. После выбора в шапке видно название роли. Локально без Docker ту же команду можно вызвать отдельно:

```powershell
cd E:\erip-main\app\backend
$env:POSTGRES_HOST=''
E:\erip-main\app\.venv\Scripts\python.exe manage.py seed_role_testers
```

Чтобы проверить сценарии по разным схемам, а не только по той, где больше лицевых счетов, заводят отдельные логины:

```powershell
cd E:\erip-main\app\backend
$env:POSTGRES_HOST=''
E:\erip-main\app\.venv\Scripts\python.exe manage.py seed_usecase_users
```

Команда проходит по действующим схемам. На каждую — `uc_<схема>_admin` (локальный администратор), `uc_<схема>_spec` (специалист начисляющей организации, вся схема), `uc_<схема>_view` (наблюдатель, только чтение). На каждого поставщика схемы — `uc_<схема>_p<код>`: специалист видит только услуги этой организации. `uc_super` видит все схемы. Пароль новых записей — `Passw0rd!x`; повтор пароль не переписывает и вторую запись не создаёт. Схемы выборки (`BR2000`, `GR5000`, `MG6000`, `MN7000`) получают логины после загрузки выборки. В Docker ту же команду запускают внутри контейнера backend.

Чтобы в фильтре «Закреплённый специалист» и в группировке по специалисту были разные люди, по схемам, где уже есть лицевые счета, заводят четырёх специалистов и раскладывают по ним свободные счета:

```powershell
cd E:\erip-main\app\backend
$env:POSTGRES_HOST=''
E:\erip-main\app\.venv\Scripts\python.exe manage.py seed_assigned_specialists
```

На каждую такую схему — Ковалёва Ольга Сергеевна, Левчук Андрей Михайлович, Гриневич Татьяна Ивановна и Савич Пётр Николаевич (`spec_<схема>_1` … `_4`, контур начисляющей организации, вся схема). Счета без специалиста и счета этих же учёток делятся по кругу. Счёт, закреплённый за другим пользователем, команда не трогает. Повтор пароль не переписывает и вторую четвёрку не создаёт. В панели фильтра реестра ЛС и договоров каждое полное имя — один пункт (`GET /api/v1/accounts/specialists/`, только контур текущего пользователя), даже если на нескольких схемах заведены однофамильцы. Выбор шлёт `assigned_name` и отбирает все такие счета контура. Группировка `group_by=specialist` подписывает строку фамилией, именем и отчеством. В колонке реестра то же полное имя. Календарь на реестре лицевых счетов, договоров, мероприятий и в претензионно-исковой работе один: плашки по группе задолженности, шапка дня/недели/месяца и три карточки справа. Щелчок по группе ставит тот же фильтр, что поиск реестра.

Идентификатор запроса (`X-Request-ID`) собирается и на обычном `http://` без сертификата: `crypto.randomUUID()` в браузере на таком адресе недоступен.

Вход по логину выдаёт access-токен в ответе (браузер держит его только в памяти вкладки, 30 минут; после перезагрузки страницы его восстанавливает refresh) и refresh в httpOnly-cookie `erip_refresh` (8 часов, одноразовый: при обновлении старый попадает в чёрный список). На `/api/v1/auth/token/` не больше 10 попыток в минуту с адреса клиента за NGINX. Выход: `POST /api/v1/auth/logout/`. Смена своего пароля: `POST /api/v1/auth/password/` (`old_password`, `new_password`) из значка настроек в шапке; все refresh этой учётной записи отзываются. Неактивная схема не пускает своих пользователей, суперадминистратор без схемы по-прежнему входит.

## Что дальше

- Отдельные процессы шлюза и адаптеров остаются на Python. Go в стек проекта не входит. Django от шлюза уже зависит только через HTTP-клиент.
- Alembic для таблиц шлюза (сейчас `create_all` и добавление колонки `claimed_at` при старте) и брокер (RabbitMQ/Kafka) вместо `BackgroundTasks`, когда воркеров станет больше двух.
- `COPY` из PostgreSQL, если пакетный `import_ais` на полной выгрузке всё ещё не укладывается в окно загрузки.
- Включить `GW_VOICE_MODE=ami`, когда заказчик даст хост, логин, секрет, контекст и шаблон канала Asterisk. Клиент AMI уже в шлюзе. Включить `GW_EMAIL_MODE=smtp`, когда заказчик даст хост SMTP и адрес отправителя схемы. Клиент SMTP уже в шлюзе. Прогон ПРИС без Минюста — `GW_PRIS_MODE=channel`. Контур Минюста — `GW_PRIS_MODE=http`, когда на сервере поднят itVPN и выданы `user_id` и ключ. Порт контура показывает `GET /gw/v1/integrations/pris/status`.
