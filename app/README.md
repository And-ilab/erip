# ЕРИП — ПМ «Модуль по работе с задолженностью» (MVP)

Каркас веб-приложения:

- **backend** — Django 5 + DRF: доменная модель, CRUD/REST, роли и контуры доступа, импорт выгрузок АИС «Расчет-ЖКУ», оповещения, журналы ошибок и аудита;
- **gateway** — FastAPI: асинхронная доставка оповещений (каналы на заглушках) и каркас интеграций ПРИС и БНП;
- **frontend** — Angular 18 + Angular Material;
- PostgreSQL 16, Redis, NGINX.

```
Angular ──/api/──> Django ──(httpx + X-Internal-Token)──> FastAPI ──> адаптеры каналов (заглушки)
                      ▲                                    │
                      └── callback статуса, ErrorLog       └──> ПРИС / БНП (заглушки)
```

`/gw/` снаружи без служебного токена отвечает 401. Браузер ходит только в `/api/`.

## Запуск в Docker

Один `docker compose up --build` из каталога `app` собирает три образа под текущий код. Nginx-образ сам ставит зависимости Angular и кладёт `dist/erip/browser`. Стили подключаются обычным файлом: отложенная вставка через `onload` не срабатывает из‑за `Content-Security-Policy` nginx, и без этого съезжают поля. Та же политика пускает подложку карты только на `https://tiles.openfreemap.org` и worker с `blob:`; без этого поле карты остаётся пустым. Шрифт иконок лежит в `ng-media`, потому что `/media/` отдаёт вложения Django, а не файлы Angular. Backend ставит шрифт DejaVu: PDF предупреждения пишется кириллицей. CSV обзвона и вложения лежат в томе `media` и отдаются по `/media/`. PostgreSQL и Redis поднимаются рядом. Повторная сборка не стирает базу: при старте backend выполняет `migrate`.

```powershell
cd app
Copy-Item .env.example .env -ErrorAction SilentlyContinue
docker compose up --build
```

Первый запуск сам готовит базу: миграции Django, схема `gateway` и схема `ais` из `postgres/ais_3nf.sql` (все таблицы 3НФ). Отдельный `migrate` и `loaddata` после `up` не нужны. Скрипты в `docker-entrypoint-initdb.d` выполняются только на пустом томе `pgdata`. Если том уже был создан раньше, схему накатывают один раз:

```powershell
Get-Content .\postgres\ais_3nf.sql | docker compose exec -T postgres psql -U erip -d erip -v ON_ERROR_STOP=1
```

Пример `.env` поднимает локальный контур с `DJANGO_SETTINGS_MODULE=config.settings.dev` и `GW_ENVIRONMENT=dev`. Вход `admin` / `admin` из `DJANGO_SUPERUSER_*`. Приложение: http://localhost:8080, Swagger шлюза: http://localhost:8080/gw/docs, админка Django: http://localhost:8080/admin/.

На сервере нужны `config.settings.prod` и `GW_ENVIRONMENT=prod`. Процесс не стартует, если `DJANGO_SECRET_KEY`, `INTERNAL_TOKEN`, `DJANGO_ALLOWED_HOSTS=*` или пароль суперадмина `admin` остались заготовками из примера. `INTERNAL_TOKEN` и `GW_INTERNAL_TOKEN` должны совпадать. Документация `/gw/docs` в prod выключена.

При старте backend применяет миграции, загружает фикстуры (`debt_group_scale`, `bnp_dictionaries`, `message_templates` — шесть каркасов писем по группам долга 1–6) и создаёт суперадминистратора. Каталог `../Примеры данных` монтируется в контейнер как `AIS_SPEC_DIR`. Если Docker не смог смонтировать путь с кириллицей, интерфейс всё равно открывается, не работает только сверка импорта со спецификациями.

Загрузка обезличенной тестовой выборки (четыре схемы: BR2000, GR5000, MG6000, MN7000; файлы лежат в `backend/fixtures/ais_sample`):

```powershell
docker compose exec backend python manage.py load_ais_sample
docker compose exec backend python manage.py link_territories
```

Без Docker, из каталога `app\backend`:

```powershell
..\.venv\Scripts\python.exe manage.py load_ais_sample
..\.venv\Scripts\python.exe manage.py link_territories
```

Для уже загруженных лицевых счетов `link_territories` нужен один раз после обновления. Новый импорт счетов раскладывает адреса сам.

## Локальный запуск без Docker

```powershell
cd app
uv venv .venv --python 3.11
uv pip install --python .venv -r backend/requirements.txt -r backend/requirements-dev.txt -r gateway/requirements.txt -r gateway/requirements-dev.txt

# backend (без POSTGRES_HOST используется SQLite)
cd backend
$env:INTERNAL_TOKEN="dev"; $env:GATEWAY_URL="http://127.0.0.1:8001"; $env:BACKEND_PUBLIC_URL="http://127.0.0.1:8000"
..\.venv\Scripts\python manage.py migrate
..\.venv\Scripts\python manage.py loaddata debt_group_scale bnp_dictionaries message_templates
..\.venv\Scripts\python manage.py createsuperuser
..\.venv\Scripts\python manage.py link_territories
..\.venv\Scripts\python manage.py runserver 127.0.0.1:8000

# gateway (в другом терминале)
cd gateway
$env:GW_BACKEND_URL="http://127.0.0.1:8000"; $env:GW_INTERNAL_TOKEN="dev"
..\.venv\Scripts\python -m uvicorn app.main:app --port 8001

# frontend (в третьем терминале) — http://localhost:4200, прокси /api и /gw
cd frontend; npm install; npm start
```

## Устройство

### Данные АИС («Примеры данных»)

- Файлы `Примеры данных/*.csv` — это спецификации полей Oracle-выгрузки (`COLUMN_NAME;DATA_TYPE;COMMENTS;MODULE_NAME`, cp1251), а не сами данные. Модели `Account`, `AccountService`, `Payment`, `Registration` построены по ним и остаются плоским слоем импорта.
- Нормализованная схема PostgreSQL (не ниже 3НФ) по тем же спецификациям — `postgres/ais_3nf.sql`, схема `ais`. Django её не мигрирует. Пустой контейнер PostgreSQL создаёт эти таблицы при первом старте. Повторный запуск скрипта остановится, если схема уже есть; снос — `DROP SCHEMA ais CASCADE`.
- Карта колонок: `backend/apps/imports/field_maps.py`. Повторяющиеся имена (`ACCOUNT_ID`, `ATTR_VALUE`, `FULL_NAME`, `CLIENT_ACCOUNT`) разводятся по порядку следования и `COMMENTS`. Колонка «Тип оплаты» без имени читается из заголовка `PAYMENT_TYPE`. Соответствие карты спецификациям проверяет тест.
- Импорт (`POST /api/v1/imports/` до 50 МБ или `manage.py import_ais` для полной выгрузки):
  - CSV (UTF-8 или cp1251, разделитель `;`, таб или запятая) и Excel (`.xlsx`, `.xlsm`, `.xls`, первый лист);
  - заголовки — либо `COLUMN_NAME` из спецификации, либо русские названия отчёта (`backend/apps/imports/header_aliases.py`);
  - подписи полей из выгрузки в реестре, карточке и выгрузке CSV совпадают с заголовками файлов выборки `fixtures/ais_sample` (рейтинг, этап воронки, группа, сценарий и специалист остаются названиями ПМ);
  - CSV команда читает потоком и пишет пакетами по 500 строк (`bulk_create` / `bulk_update`); книга Excel читается целиком;
  - upsert по ключу; повтор одного ключа внутри пакета оставляет последнюю строку;
  - повторная загрузка не меняет данные;
  - строки чужой схемы отклоняются;
  - журнал пишется в `ImportJob`;
  - после импорта ЛС, услуг, оплат и регистраций пересчитываются группа, дата возникновения, рейтинг, сценарий, этап воронки и контакты из АИС, пакетами по 500 лицевых счетов. Ручная группа хранится отдельно и снимается, только если расчётная группа изменилась относительно основания корректировки.
- Исходная строка сохраняется в `raw`. `manage.py purge_retained` очищает `raw` старше `RAW_RETENTION_DAYS` (по умолчанию 90), `AuditLog` старше `AUDIT_RETENTION_DAYS` (365) и `ErrorLog` старше `ERROR_LOG_RETENTION_DAYS` (90). Команду ставят в планировщик, она не вызывается на каждый запрос.
- Списки лицевых счетов опираются на индексы `(organization, provider_id, debt_group)` и `(organization, balance_out)`. На PostgreSQL миграция `0005_pg_trgm` создаёт расширение `pg_trgm` и GIN-индексы по ФИО, адресу и идентификационному номеру. Роли БД нужно право `CREATE EXTENSION`, иначе расширение создают один раз отдельно и миграцию прогоняют снова.
- В спецификации `DEBT_PERIOD` имеет тип DATE, но по описанию это число месяцев долга. Хранится как целое, это стоит уточнить у команды АИС.
- Тариф и количество по услуге хранятся с десятью знаками после запятой: в отчёте встречаются значения вроде `0,20745` и `1,3333333333`.
- Обезличенная выборка `backend/fixtures/ais_sample`: 160 лицевых счетов, 2974 договора услуг, 69 оплат, 792 регистрации. В файлах остались следы Excel: УЕН и часть телефонов записаны как `1,2E+11` (точные цифры не восстановить, числовой УЕН не заполняется, текст остаётся в `raw`); «Доля по документу» местами выглядит как `01.янв`; «Статус пачки» и «Способ распределения» — слова, не коды, они остаются в `raw`. Девять договоров повторяют один ID услуги с разными названиями, сохраняется последняя строка. У GR5000 во всех услугах «Кол-во периодов долга» равно 0, поэтому группа не поднимается выше 1.

### Реестр и карточка (ТЗ 4.2.1, 4.2.2)

- Реестр ЛС: серверный список (колонки включают числовой код ЛС, ИН и УНП отдельно), канбан по этапу воронки (колонки «Новый должник», «Автообзвон/уведомления», «Предупреждение вручено», «Отключение услуг», «Испол. надпись / иск», «ОПИ», «Не должник»). На карточке канбана: ФИО, номер ЛС и адрес с улицы, буква рейтинга и группа, сумма долга и пеня, контрольная дата (вручение, наряд, подача или срок) и инициалы закреплённого специалиста. Смена этапа — значок в углу карточки или перетаскивание карточки в другую колонку; несколько отмеченных карточек переносятся вместе. Наблюдатель и поставщик этап не меняют. В списке строку отмечают флажком, щелчком с Ctrl или протягиванием мыши по строкам; заголовки колонок перетаскиваются, порядок сохраняется. Календарь контрольных дат. Кнопка «Календарь» открывает правую панель: «Виды отображения» (день, неделя, месяц, год), «Выбор дня/диапазона» (матрица, стрелки, «Сегодня» и «Фильтры») и «Отображение событий» (вкл/выкл). Первый щелчок задаёт день, смена месяца и года его не сбрасывает, второй щелчок закрывает диапазон; цифры начала и конца остаются видны. Щелчок по событию открывает карточку мероприятия, лицевого счёта или договора. Щелчок по дню на доске создаёт мероприятие на эту дату по текущему фильтру реестра (`due_on`). «Фильтры» закрывает панель и открывает тот же поиск: группы, рейтинг, этап, избранное. Запрос уходит с `date_from` и `date_to`. Карта, строка поиска: по нажатию выпадает панель «Фильтры / Группировать по / Избранное» (несколько групп и несколько рейтингов, этап, свой набор). Группировка по организации, группе, рейтингу, категории, специалисту или периоду. Экспорт CSV. Кнопка «Мероприятие» запускает партию по отмеченным счетам, а если отметки нет — по всем счетам текущего фильтра. Шаблон выбирается из действующих (`GET /api/v1/templates/`), в партию пишется его название. Поставщик, а также отключение и взыскание, отмечают виды услуг из `GET /api/v1/services/choices/`; запуск передаёт `catalog_service_ids`, и сервер берёт строки этих услуг на счетах фильтра. Канал уведомления в этой панели — только SMS или e-mail. Набор колонок по-прежнему читается с сервера, чекбоксы колонок со страницы убраны. Обзвон передаёт шаблон, окно времени и CSV с номером по правилу источника. Уведомление выбирает канал и шаблон. Предупреждение сохраняет PDF. Отключение и взыскание требуют отмеченные услуги, а не все услуги ЛС. Взыскание создаёт задание исполнителю и срок. Смена сценария берёт название и дату начала.
- Карта — ещё один вид того же реестра (`GET /api/v1/accounts/map/`, кнопка «Карта»). В браузер уходит один уровень дерева: щелчок по пузырю запрашивает его детей. Путь для Минска: Минская область → Минск → район города → микрорайон, если он есть в адресе → улица → дом. Фаниполь и Дзержинск без района в адресе висят прямо на Минской области; если район в адресе написан, он остаётся родителем города. Число в пузыре — лицевые счета поддерева с учётом контура и фильтра группы, рейтинга и этапа. У поставщика пузырь тоже один на место: суммы его услуг в запрос карты не подмешиваются, иначе каждый лицевой счёт рисуется отдельным кружком с числом 1. Цвет — группа, которой в этом месте больше; при равенстве берётся старшая. Щелчок по дому открывает список этих счетов (`territory` в фильтре списка). Пустой адрес в дерево не попадает и в списке остаётся. Уже загруженные счета раскладывает `manage.py link_territories` (повтор безопасен). `manage.py seed_minsk_accounts` добавляет 20 лицевых счетов с кодами 90000001–90000020 в ту же схему, что и уже загруженный счёт, сразу раскладывает их и ставит рейтинг по группе. Повтор не создаёт дубликаты и другие счета не меняет. `manage.py seed_two_suppliers` добавляет схему `test_two` (ЖЭС 9301 и ЖКХ 9302, три лицевых счёта 93000001–93000003). У каждой услуги свой остаток и пеня, число месяцев долга соответствует группе (2, 3 и 6 месяцев), пересчёт строит периоды и доли, адреса с районом и известной улицей сразу кладутся на карту. Учётки `test_zhes`, `test_zhkh` и `test_spec`, пароль `Passw0rd!x`. Повтор обновляет суммы и привязку. `manage.py seed_demo_contours` добавляет две схемы (`demo_minsk`, `demo_fanipol`), в каждой ЖЭС-1 и ЖЭС-2 и поставщиков воды, газа и электричества, по шесть лицевых счетов с разными наборами услуг и пользователей контуров. Пароль новых учёток `Passw0rd!x`: `demo_spec_minsk`, `demo_spec_fanipol` видят свою схему целиком; `demo_water_minsk`, `demo_gas_minsk`, `demo_power_minsk` и такие же с суффиксом `_fanipol` видят только свою услугу. Повтор не плодит записи и пароль уже созданных учёток не меняет. Улица из списка известных точек встаёт на свои координаты; дом сдвигается от этой точки на несколько сотен метров, чтобы пузыри одного дома не совпали. Улица вне списка считается от центра родителя, а не от кадастрового адреса. Первое открытие карты делает то же для счетов с адресом, у которых узла ещё нет. Новый импорт лицевых счетов делает это сам. Подложка карты пока публичная (OpenFreeMap) и в проде заменяется файлом PMTiles на NGINX. Координаты дома из АИС не приходят: известные области и города ставятся на свои точки, остальные сдвигаются от родителя.
- Карточка ЛС: услуги только с остатком, регистрации с ролью «плательщик / солидарный должник», история остатка по каждому периоду долга, вкладка документов с фильтрами по сумме, пене, оплате и датам и вложенными видами, контакты ПМ с приоритетом, правкой и удалением, категории справочника с карточки, чек-лист исполнительной надписи и пакет документов, список мероприятий и переход в реестр. Сумма долга в шапке и исходящее сальдо на вкладке «Общие» открывают состав: кому из поставщиков и сколько основного долга и пени приходится. Доли хранятся в `DebtShare` и пересобираются при пересчёте ЛС и при открытии состава (`GET /api/v1/accounts/{id}/debt-shares/`). Если исходящее сальдо ЛС больше суммы услуг, начисляющая организация видит строку «Не разнесено по поставщикам». «Обновить сейчас» сразу пересчитывает ЛС по уже загруженной выгрузке и не подменяет время обновления из АИС.
- Оформление: палитра задана CSS-переменными `--erip-*` в `frontend/src/styles.scss` (тёмно-бирюзовые шапка и левое меню, золотой акцент, зелёный «выполнено», красная пеня), там же общие классы `.surface`, `.chip`, `.alert`, `.rating-badge`, `.group-badge`, `.kind-chip`, `.status-pill`. В шапке карточки ЛС: крошки, полоса этапов воронки по `funnel_stage` (только показ, этап меняется в канбане), ФИО, бейджи группы и рейтинга, ключевые суммы. Пеня в шапке — сумма `balance_mulct_out` по услугам из АИС. Флаги наследственного дела и банкротства показаны плашкой. У чек-листа исполнительной надписи есть полоса прогресса, кнопка пакета остаётся неактивной до закрытия всех пунктов. В реестре группа и рейтинг выводятся цветными бейджами. Карточка канбана повторяет макет: полоса цвета группы слева, кружок с буквой рейтинга, подпись «Группа N», сумма и пеня, дата внизу и кружок с инициалами специалиста. Реестр мероприятий повторяет макет: строка поиска с чипом периода, группы статусов в одной таблице, под ней матрица по типам. Карточка мероприятия красится по виду (обзвон, письмо, предупреждение, отключение). Денежные суммы на экране сопровождает знак белорусского рубля: буква «Б», горизонтальная черта на четверти высоты снизу режет округлую часть пополам. Готового знака в шрифтах нет, его рисует интерфейс.
- Реестр договоров (`/contracts`): сводка поставщика (число ЛС с долгом, долг, пеня, мероприятия), список лиц с ИН и УНП отдельно, числом ЛС, суммой и ранним периодом, список услуг, канбан по этапу с той же плотностью, что у карточки лицевого счёта: плательщик, ИН или УНП, число ЛС и услуг, название услуги, улица, группа, категория, долг и пеня, срок погашения или дата возникновения долга. Карточку перетаскивают левой кнопкой в другую колонку или выбирают этап значком в углу: этап ставится всем лицевым счетам этого должника в видимом контуре и дальше не затирается пересчётом. Несколько карточек отмечают с Ctrl и переносят вместе. Наблюдатель и поставщик этап не меняют. Чужой счёт и несколько схем в одном переносе отклоняются (`POST /api/v1/contracts/stage/`). Календарь сроков погашения и контрольных дат — та же правая панель: виды отображения, выбор дня или диапазона и переключатель событий вкл/выкл. Событие открывает карточку, день на доске создаёт мероприятие по фильтру договоров (`POST /api/v1/contracts/events/`). «Фильтры» открывает панель поиска. строка поиска открывает панель «Фильтры / Группировать по / Избранное» (группы, категория, этап, обслуживающая организация по названию или коду, сохранённый набор), группировка. Карточка договора собирает услуги этого поставщика по всем ЛС должника: лицо (физлицо или юрлицо), остатки по периодам, срок погашения, регистрации с членом семьи, социальной категорией, нетрудоспособностью и наследством, контакты с режимом обзвона, категорию, фактическое проживание, флаг наследства со сроком, мероприятия и журнал. Правило обзвона (день месяца и часы только мобильного) читается из `GET /api/v1/nsi/calculation-settings/`, суперадминистратор сохраняет его с реестра. Колонки «Схема», «Поставщик» и «Обслуживающая организация» показываются, только если в области пользователя таких организаций больше одной. Признаки приходят в `GET /api/v1/auth/me/` (`show_schema`, `show_supplier`, `show_service_org`). Суперадминистратор видит все три. Локальный администратор, специалист и наблюдатель одной схемы не видят колонку схемы: её имя уже в шапке; поставщика и обслуживающую организацию видят, если в схеме их несколько. Поставщик с одной организацией не видит своё имя в строках; если к нему привязано несколько поставщиков или его услуги сидят на счетах разных ЖЭС, соответствующие колонки остаются. Наблюдатель не запускает мероприятия, не правит карточку и не формирует отключение. Поставщик не меняет группу и не формирует задание на отключение: факт приостановления фиксирует он. Шаблоны сообщений в меню есть у начисляющей организации, которая их правит или отправляет. Поставщик не видит чужие услуги: пустой список его организаций означает пустой реестр, а не всю схему. Сальдо карточки ЛС (входящее, исходящее, начислено, оплата), группировка реестра, документы, вложения и мероприятия режутся по его `provider_id`. В составе долга ему видна только своя доля. Два поставщика ставят одно и то же мероприятие независимо: у партии пишется `owner_provider_id`, чужая партия в карточке ЛС и в реестре мероприятий не показывается. Смена сценария поставщиком запирает сценарий только его услуг. Общее мероприятие начисляющей организации (без поставщика-автора) по-прежнему видно, если в партии нет услуг или есть его услуга. Предупреждение и отключение с чужой услугой отклоняются, как и запись работы с задолженностью по чужой услуге. Поставщик не меняет группу, сценарий всего лицевого счёта, этап воронки и исполнителя. Факт приостановления и возобновления записывает только `POST /api/v1/measures/{id}/confirm/` с `action` `suspend` или `resume` и `source` `pm` или `ais`. `STOP_DATE` — дата окончания договора, пересчёт по ней приостановление не подтверждает. Поставщик создаёт обзвон, уведомление и предупреждение только с указанием своей услуги. Назначение категории сразу пересчитывает сценарий по правилу группа+категория. У специалиста начисляющей организации категория и наследственное дело расходятся на все ЛС с тем же ИН или УНП; у поставщика — только на счета, где есть его услуга. Пустые ИН и УНП не склеивают разных должников: канбан и список лиц считают одну карточку на ключ в SQL. Смена фильтра на открытом канбане, календаре или группировке запрашивает этот вид заново. Канбан договоров — одно дело на должника. Контакт ПМ можно привязать к зарегистрированному лицу. Статус юрлица: действующее, ликвидация или банкротство. Наследственное дело ставит автомеры в «Приостановлено» и возвращает их в «Назначено», когда флаг снят, срок прошёл или в выгрузке появился новый плательщик. Исходящее сальдо услуги и пеня — разные колонки выгрузки; начальный долг копирует сальдо, начальная пеня — колонку пени.
- Группа услуги считается по числу месяцев до самого раннего непогашенного периода (`debt_period`). Весь остаток и пеня сидят на этом раннем периоде, поздние месяцы окна хранят ноль: в CSV нет суммы каждого месяца. Дата возникновения — день после срока оплаты раннего периода (`payment_due_day`, по умолчанию 25). Отключение и взыскание запускаются только по услуге группы 3 и старше; младшая услуга на том же счёте в партию не попадает. Обзвон один на счёт и отбирается по старшей группе счёта. Рейтинг A–E. Подрейтинг растёт при новом входе в ту же букву за `rating_period_months`, а не при каждой ночной загрузке. Без долга остаётся A без номера. D — группы 4–5 и признак «не занят в экономике» или банкротство. Правило сценария с категорией должника перекрывает правило группы. Полное погашение снимает сценарий, в том числе назначенный вручную, и закрывает активные мероприятия. Параметры: `GET/PATCH /api/v1/nsi/calculation-settings/current/` (там же `warning_wait_days` — срок оплаты после вручения предупреждения, и `disconnect_requires_approval` — согласовывать ли отключение). Новая загрузка со сменой плательщика снимает флаг наследственного дела; пока он стоит, автоматические мероприятия не создаются. Ручная смена группы, если специалист закреплён, кладёт ему сообщение во входящие. Категории: `/api/v1/nsi/debtor-categories/`.
- Реестр мероприятий (`/measures`): список сгруппирован по статусу (назначено, выполняется, завершено, ошибка, приостановлено, прервано). Над списком строка про группу 2: срок оплаты после предупреждения (`warning_wait_days`, базово 5 дней) и переход к счетам, готовым к отключению. Кнопка скачивания собирает CSV уже загруженных строк. В строке — название из вида и шаблона, должник и номер ЛС из видимого контура, исполнитель, следующее действие по статусу и сроку. Поиск `search` идёт по номеру ЛС, ФИО, шаблону, сценарию и примечанию. Вид находится по началу названия, если в запросе не меньше четырёх символов. `period=ГГГГ-ММ` оставляет мероприятие, чей срок пересекает месяц; без даты окончания оно остаётся в месяце начала. У завершённого в колонке «Следующее действие» написано «Завершено», срок — отдельной фразой; дата отключения и возобновления берётся из факта. «Показать ещё» дочитывает группу (`status` и `offset`, по 40) и матрицу (`offset`, по 200): `GET /api/v1/measures/registry/` и `GET /api/v1/measures/matrix/`. Поставщик видит свою партию и общее мероприятие схемы, если в нём нет услуг или есть хотя бы одна его услуга. Партия другого поставщика с тем же видом ему не видна. Число ЛС в партии считается только по счетам, которые пользователь и так видит. Просмотр реестра и матрицы пишется в аудит одной записью. У партии в ответе есть `progress` — сколько частных мероприятий видно пользователю (`total`) и сколько из них завершено (`done`).
- Карточка партии (`/measures/{id}`): слева вид, шаблон или канал, даты, окно обзвона и следующее действие, справа — сколько ЛС завершено с полосой прогресса. Ниже список лицевых счетов партии, а под ним журнал переходов: когда, кто, было → стало, основание. Колонки списка зависят от вида: у обзвона телефон и результат, у уведомления адресат и время отправки, у предупреждения способ вручения и статус отправления, у отключения даты приостановления и возобновления. Блоки действий появляются только когда они применимы: согласование видит локальный администратор, «Принять задание» — специалист поставщика, отмена исчезает, как только услуга приостановлена. Строка открывает форму результата прямо в таблице. Переход между карточками перечитывает партию по смене id, а не только при первом открытии.
- Третий вид реестра — «Готовы к отключению» (иконка `power_off`): лицевые счета с истёкшим сроком предупреждения, непогашенным долгом и услугами, которые можно отключать. Отметка счёта включает все его услуги, отдельные услуги снимаются флажками. Кнопка создаёт партию отключения и открывает её карточку. В списке партий у строки видно, сколько ЛС уже завершено, а название ведёт в карточку. На вкладке «Мероприятия» карточки ЛС рядом со статусом партии показывается статус по этому лицевому счёту.
- Частное мероприятие (`MeasureItem`): по одной записи на каждый ЛС партии, со своим статусом (назначено, выполняется, завершено, прервано пользователем, завершено с ошибкой), телефоном или адресатом, результатом и примечанием. Статус партии пересчитывается по частным записям; пауза по наследственному делу пересчётом не снимается. Каждый переход пишется в `MeasureEvent` (кто, было, стало, основание). Состав партии отдаёт `GET /api/v1/measures/{id}/` — только те ЛС, которые видит пользователь.
- Отбор при запуске (`POST /api/v1/measures/`) принимает услуги первичными ключами строк (`service_ids`) или кодами услуг АИС (`catalog_service_ids`): второе раскрывается в строки на уже отобранных счетах внутри контура. Ответ 201 и поле `skipped`: по каждому непрошедшему ЛС — номер и причина. Обзвон оставляет только номера, приводимые к +375; юридические лица участвуют по флагу `call_legal`; диапазон `group_from`–`group_to` режет по группе долга. Уведомление принимает только `email` или `sms` и требует адресата (мессенджеры на этом этапе не подключаются). По всем видам, кроме передачи взыскания, ЛС с открытым наследственным делом пропускается. Если не прошёл ни один ЛС — 400 с тем же `skipped`. В плашке ошибки одинаковые причины схлопываются в счётчик, например «Нет номера +375 (27)».
- Результат фиксирует пользователь: `POST .../result/` с `item_id` (для обзвона — `call_result`, длительность и доля прослушивания; дозвон закрывает запись, неверный номер помечает ошибкой, недозвон и занято оставляют в работе), `POST .../send/` ставит письма и SMS в оповещения и переносит ошибку доставки в частное мероприятие, `POST .../deliver/` проставляет вручение предупреждения (способ, дата, ФИО получившего либо акт об отказе).
- Отключение: вручение предупреждения задаёт срок оплаты (`warning_wait_days`, по умолчанию 5 дней). До истечения срока отключение не запускается — нужна записанная причина в `override_reason`. `GET /api/v1/measures/ready-to-disconnect/` показывает ЛС с истёкшим сроком, непогашенным долгом и услугами, которые вообще можно отключать. Если в справочнике включено `disconnect_requires_approval`, список уходит локальному администратору: `POST .../approve/` или `.../reject/` с причиной. Согласованное задание падает во входящие специалистам поставщика. `POST .../accept/` принимает только пользователь контура поставщика и двигает этап воронки. `POST .../confirm/` с `action` = `suspend` или `resume` и `source` = `pm` или `ais` фиксирует факт. `POST .../cancel/` с причиной отменяет задание, пока поставщик не приостановил услугу; после приостановления отмена запрещена.
- Оплата не включает услугу обратно сама: погашение закрывает открытые частные мероприятия, а уже приостановленное отключение оставляет и кладёт закреплённому специалисту задание проверить возобновление.

### Оповещения

1. Каркас выбирается по группе долга ЛС (`effective_group`: ручная, иначе расчётная) и каналу: локальный шаблон схемы, иначе центральный из фикстуры `message_templates` (группы 1–6, канал e-mail). `POST /api/v1/notifications/` может не передавать `template` — тогда каркас подставится сам. В контекст попадают `{fio}`, `{account}`, `{amount}`, `{address}`, `{debt_group}`, `{group_name}` — эти ключи берутся только из лицевого счёта, поля из запроса их не затирают. Название группы отдаёт карточка ЛС (`group_name`). На вкладке «Оповестить» каркас этой группы уже выбран, ниже показан текст с подставленными данными счёта, кнопка отправки блокируется до ответа сервера. Повтор с тем же автором, ЛС, шаблоном и каналом, пока статус `new` или `queued`, возвращает уже созданное оповещение и в шлюз не уходит. `POST .../resend/` в этих статусах отвечает 400. Приветствие шлюз добавляет отдельно. Шаблоны правятся в «Настройке», блок «Шаблоны сообщений» (поле «Группа долга»). Адрес /templates открывает ту же страницу. Кнопка «Деактивировать» сначала спрашивает подтверждение и переносит шаблон в блок «Архивированные». Оттуда его возвращает «Вернуть из архива» (`POST /api/v1/templates/{id}/restore/`).
2. `NotificationDispatcher` (зависит от абстракции `GatewayClient`) → `HttpGatewayClient` асинхронно через `httpx.AsyncClient` → `POST /gw/v1/notifications` с заголовком `X-Internal-Token` (ответ 202). Адрес callback шлюз собирает сам из `GW_BACKEND_URL` и id оповещения, поле из запроса не принимается.
3. Шлюз пишет `delivery_log`, в фоне формирует текст декоратором `@with_greeting` («Добрый день, {имя}! … С уважением, ЖКУ») и передаёт его адаптеру канала из `AdapterRegistry` (`inbox`, `email`, `sms`, `voice` — заглушки). В шаблоне подставляются только простые имена `{fio}`, `{account}` и т.п.
4. Итог шлюз возвращает в backend: `POST /api/v1/notifications/{id}/delivery-status/` с заголовком `X-Internal-Token` (до трёх попыток). Статус становится `sent` или `failed` и тем же вызовом переносится в частное мероприятие, если письмо или SMS поставило уведомление из реестра мероприятий: ошибка доставки видна в строке ЛС. Перед отправкой строка журнала атомарно переводится из `accepted` в `processing`, поэтому два процесса uvicorn не отправляют одно сообщение дважды. Зависшую доставку (дольше 2 минут) шлюз забирает снова при старте. Завершённые записи `delivery_log` старше `GW_LOG_RETENTION_DAYS` (по умолчанию 90) удаляются при старте.
5. `context: {"_fail": true}` имитирует отказ канала. Ошибка попадает в `ErrorLog` с тем же `X-Request-ID`, что у исходного запроса.

### Границы модулей

Приложения Django — будущие сервисы. Сейчас они в одном процессе и одной базе, HTTP-границы уже разделены.

| Контекст | Где | Что выносить первым |
|---|---|---|
| Пользователи и доступ | `apps/users`, `AccessScope` | Проверка контура и списка организаций |
| Реестр задолженностей | `apps/debts/views.py` вызывает `apps/debts/services/` | Группа, рейтинг, наследство, реестр договоров (`services/contracts.py`) |
| Загрузка АИС | `apps/imports` | Пакетный приём файла; пересчёт вызывает сервисы реестра, не представления |
| Справочники | `apps/nsi` | Шкалы, сценарии, параметры расчёта |
| Оповещения | `apps/notifications` | Уже ходит в шлюз по HTTP |
| Шлюз доставки | `app/gateway` | Уже отдельный процесс |

Представление не содержит правила должника и поставщика: оно проверяет запрос и вызывает функцию сервиса. Другой контекст не импортирует `views`. Общая база — временная связка; замена её на вызов сервиса не должна трогать шаблоны Angular.

### Паттерны

| Паттерн | Где |
|---|---|
| Singleton | `gateway/app/core/singletons.py` (`Database` — пул `AsyncEngine`, `HttpClient` — общий `httpx.AsyncClient`), `get_gateway_client()` в Django. Соединениями Django с БД управляет ORM (`CONN_MAX_AGE`) |
| Decorator | `@with_greeting`, `@api_response` (конверт `{"data", "meta": {"request_id", "duration_ms"}}`) |
| Strategy / Adapter | `ChannelAdapter` + `AdapterRegistry`; `PrisClient` / `BnpClient` со Stub- и Http-реализациями |
| Repository | `apps/debts/repositories.py` |
| DIP / OCP | Dispatcher зависит от `GatewayClient`; новый канал — новый класс и `registry.register(...)` |

### Интеграции («Информация по интеграции»)

- **ПРИС:** схемы запросов и ответов по регламенту (`PutClaimantSaveDataDebt`, `PutClaimantSaveRepayDebt`, `GetClaimantInfoBy*`, `GetNSIData`), авторизация `x-user_id` / `x-accesskey` → `x-token` + `x-timestamp`, кэш токена (память или Redis) на 30 минут. По умолчанию `GW_PRIS_MODE=stub`; `http` включает `HttpPrisClient` после получения доступа к тестовому контуру.
- **БНП:** манифест заявления (`BnpManifest`) с проверками:
  - `personType` и условно обязательные поля;
  - структура личного номера (14 символов) и УНП;
  - `amount` в формате `10.00`, даты в формате `YYYY-MM-DD`;
  - `serviceId`, `typeId` и `docType` — по справочникам БНП;
  - документы только `.pdf`, не более 15 МБ.

  Справочники извлекаются из `Справочники БНП.docx` скриптом `scripts/extract_bnp_dictionaries.py`.
- Проверочные эндпоинты: `/gw/v1/integrations/pris/echo`, `/pris/claimant-info`, `/pris/save-data-debt/validate`, `/bnp/validate`, `/bnp/dictionaries`.

### Логи и ошибки

- JSON-логи в stdout (поля `timestamp`, `level`, `service`, `request_id`, `user_id`, `path`, `message`), формат готов к ELK/OpenSearch.
- Необработанные ошибки backend и ошибки шлюза пишутся в `ErrorLog`: `/api/v1/audit/errors/` и раздел «Журнал ошибок», доступны только суперадминистратору.
- Просмотр карточки ЛС и изменения записываются в `AuditLog`. Список и поиск лицевых счетов и регистраций пишут одну строку на запрос (фильтры и страница), а не строку на каждую запись. В списке регистраций идентификационный номер маскируется, в карточке ЛС он полный. IP в журнале — адрес, который NGINX дописал в `X-Forwarded-For` (`NUM_PROXIES=1`).

### Роли (MVP)

- `superadmin` — все схемы.
- `local_admin` — своя схема: специалисты и наблюдатели, шаблоны, импорт. Другого локального администратора и суперадмина он не видит и не назначает.
- `specialist` — реестр, карточки, оповещения.
- `contour=supplier` — пользователь видит только услуги, где его организация назначена поставщиком (`AccountService.provider_id`), и лицевые счета, на которых такие услуги есть. Пустой список организаций поставщика даёт пустой реестр. Суммы долга на карточке и в группировке — только его услуги. По умолчанию контур `billing`: видимость по обслуживающей организации лицевого счёта.
- `observer` — только чтение.

### Взыскание и сценарии (показ заказчику)

Разделы открываются из левого меню, в том числе «Настройка» — конструктор сценариев. Списки лицевых счетов, дел, договоров и таблицы на карточках лежат в окне высотой не больше десяти строк: колесо прокручивает это окно, страница от длины списка не растёт. Список мероприятий занимает оставшуюся высоту окна и тянется по ширине вместе с фильтром; страница за край окна не растёт. Под окном остаётся переключатель страниц, где он уже был. На мероприятиях и в претензионно-исковой работе тот же фильтр, что на реестре ЛС: поиск, группа, рейтинг, этап и избранное; у мероприятий ещё месяц. На реестре ЛС, реестре договоров, мероприятиях и претензионно-исковой работе один и тот же переключатель: список, канбан, календарь и «Граф. аналитика». Меняется состав, картинка та же. На договорах в списке остаются срезы «Лица» и «Услуги», на мероприятиях рядом — скачивание списка и «к отключению». Графики: `GET /api/v1/accounts/charts/?scope=` пустой — все ЛС контура, `measures` — ЛС с мероприятиями, `claims` — группа 3 и старше, открытое дело, этап надписи или ОПИ, либо мероприятие «взыскание», `contracts` — ЛС с услугами. Претензионно-исковая работа показывает должников с группы 3, с мероприятием «взыскание» или с открытым делом. Список, канбан, календарь и графики берут одну выборку (`scope=claims` на `GET /api/v1/accounts/`, `.../kanban/` и `.../calendar/`). Канбан этого раздела — пять колонок по 2–3 этапа: пакет (очередь, подготовка, нотариус), ответ нотариуса, суд, ОПИ и итог. Карточка та же, что в реестре лицевых счетов, на ней строкой написан точный этап. Перенос левой кнопкой ставит дело на входной этап колонки, значок выбирает точный этап. Обязательный шаг без даты вручения, тарифа или записанной причины не проходит. В списке без открытой карточки — таблица этих должников. Открытое дело занимает всю ширину раздела, колонки должников рядом с карточкой нет; назад ведёт «К списку». Кнопка-сетка слева от «ЕРИП · Работа с задолженностью» сворачивает левое меню до иконок: название пункта — во всплывающей подсказке. `GET /api/v1/claims/` по-прежнему отдаёт дела и очередь `assigned`. «Добавить исполнительную надпись» открывает карточку фиксированной высоты: лицевой счёт выбирается из выпадающего списка не длиннее 12 строк, он закрыт, пока поле не нажато, и ищет с двух символов. Дальше период, дата вручения, суммы из АИС, тариф, пакет. Счёт группы младше 3 из этой формы не оформляется — для группы 2 остаются предупреждение и приостановление услуг. У группы 4 и старше на карточке видна ветвь выселения и отчуждения. Дело ведёт лицевой счёт: дата вручения предупреждения и нотариальный тариф обязательны для статуса «Направлено нотариусу». Отказ нотариуса открывает иск и записывается только с комментарием или с постановлением об отказе на карточке счёта. Другой файл счёта отказ не проводит. Комплект надписи показывает эти файлы: расчёт, доверенность, скан. Поля выселения и даты пакета видны, когда вид иска — выселение или отчуждение. «Невозможность взыскания» требует акт ОПИ, списание — три акта и согласие всех выбранных согласующих. Отказ одного акт не формирует. Статус «Взыскано» включается после отметки, что выгрузка АИС принесла погашение долга, пени и тарифа; само сальдо при этом не переписывается.

Кнопка «Направить нотариусу» возвращает номер `stub-…` и прямо пишет, что в личный кабинет БНП пакет не уходил. Статус ОПИ сохраняется вручную, сервисы 3.11.01–3.11.05 не вызываются. Итог списания помечает, что файл в АИС ещё не выгружен.

«Настройка» в левом меню — конструктор шагов: слева таблица мер, справа условия (группы, категория, тип организации, ФЛ/ЮЛ, телефон, оплата, предыдущий шаг), действие и переход. Назначение опубликованного сценария запускает первый подходящий шаг и пишет на мероприятии версию сценария. Пауза хранит историю и причину. Центральный «Стандартное взыскание» копируется в схему. Публикация поднимает версию. Без галки «Перевести уже запущенные счета» назначенный лицевой счёт остаётся на своей версии. Шаг «мессенджер» сохраняется и не отправляет сообщение. Печатная форма — страница из блоков (логотип, реквизиты, текст, подпись): их порядок, шрифт, отступ и выступ видны на макете. PDF собирается по этому порядку (один счёт или пакет до 100); адресат — должник, поставщик или администрация района. Файл остаётся на версии макета. Шаблоны сообщений на том же экране: список, архив, предпросмотр и версии. Откат создаёт новый номер, уже отправленное оповещение помнит старый. Шаг сценария хранит идентификатор шаблона: переименование не отвязывает шаг. Старый шаг без идентификатора остаётся на записанном имени. «Настройка методологии» на том же экране у суперадминистратора: границы групп без пересечений и пропусков, пороги рейтинга A–E и дни мобильного номера. Сохранение не переписывает строки истории; галка применяет новые пороги к текущим буквам. Признак «звонить юридическим лицам» задаётся на схеме и, отдельно, на сценарии.

Канбан и список «Взыскания» берут адрес, группу, рейтинг, пеню и специалиста с лицевого счёта. Чтобы окна не были пустыми, по свободным счетам раскладывается выборка:

```powershell
cd E:\erip-main\app\backend
$env:POSTGRES_HOST=''
E:\erip-main\app\.venv\Scripts\python.exe manage.py seed_claim_sample
```

Команда открывает до восьми дел на разных этапах, центральный сценарий и макет предупреждения. Уже открытые вручную дела она не переписывает. Для Docker ту же команду запускают внутри контейнера backend после `docker compose up --build -d`.

«Граф. аналитика» на этих разделах открывает одни и те же три вида: столбцы по этапам воронки (тёмная часть — основной долг `balance_out`, светлая — пеня `balance_mulct_out`), две круговые доли дел и суммы по группам 1–6, линия динамики по месяцам. Подпись над графиком называет раздел. Группа на круговой — действующая группа лицевого счёта (ручная, если задана). `GET /api/v1/accounts/charts/` режется тем же контуром, что реестр, и параметром `scope`, как в абзаце выше: поставщик суммирует только свои услуги. Месяцы — последние 12 срезов `BalanceHistory`; если истории нет, на линии одна точка текущего среза (`months_source`: `history` или `current`). Просмотр пишет одну строку аудита. Кнопка «Экспорт CSV» собирает файл в браузере из уже загруженной сводки. На реестре ЛС у переключателя есть ещё карта.

- `GET /api/v1/accounts/charts/`
- `GET/POST /api/v1/claims/`, карточка `GET/PATCH /api/v1/claims/{id}/`
- `POST .../send-notary/`, `.../notary-result/`, `.../acts/`, `.../opi/`, `.../ais-receipt/`, `.../writeoff/`, `.../decide/`, `.../move/`
- `GET/POST /api/v1/nsi/scenarios/`, `POST .../copy/`, `.../publish/` (`apply_to_running`), `.../restore/`, `.../assign/`, `GET/PATCH .../calling/`
- `GET/POST /api/v1/nsi/print-forms/`, `POST .../render/` (`account` или `accounts`, до 100), `GET .../documents/{id}/`, `GET .../package/{batch}/`, `POST .../restore/`
- `PUT /api/v1/nsi/debt-groups/replace/`, `PATCH /api/v1/nsi/calculation-settings/current/` (`apply_recorded`), `POST /api/v1/templates/{id}/rollback/`

Контур доступа реализован в одном месте, `apps/users/scoping.py`, и действует и для списков, и для запросов по id. Оповещение по лицевому счёту дополнительно ограничено назначенными обслуживающими организациями. «Прочитано» ставит только получатель.

На экране входа справа от логина и пароля — временные кнопки ролей (суперадминистратор, локальный администратор, специалист, наблюдатель, поставщик, Тест ЖЭС). Они вызывают `GET/POST /api/v1/auth/stub-role/` и работают только при `DEBUG` (локальный `config.settings.dev`). В проде маршрут отвечает 404, кнопки не показываются. Учётные записи `stub-*` создаются при нажатии, пароль у них не задан. Специалист, локальный администратор, наблюдатель и поставщик привязываются к схеме, в которой больше всего лицевых счетов; поставщик дополнительно ограничивается организациями с признаком поставщика. «Тест ЖЭС» — тот же контур поставщика, но одна организация: поставщик с наибольшим числом услуг. В шапке у поставщика с одной организацией показано её краткое имя, рядом — имя пользователя. Подробности и как убрать — в [STUBS.md](STUBS.md).

Идентификатор запроса (`X-Request-ID`) собирается и на обычном `http://` без сертификата: `crypto.randomUUID()` в браузере на таком адресе недоступен.

Вход по логину выдаёт access-токен в ответе (браузер держит его только в памяти вкладки, 30 минут; после перезагрузки страницы его восстанавливает refresh) и refresh в httpOnly-cookie `erip_refresh` (8 часов, одноразовый: при обновлении старый попадает в чёрный список). На `/api/v1/auth/token/` не больше 10 попыток в минуту с адреса клиента за NGINX. Выход: `POST /api/v1/auth/logout/`. Смена своего пароля: `POST /api/v1/auth/password/` (`old_password`, `new_password`) и пункт «Смена пароля»; все refresh этой учётной записи отзываются. Неактивная схема не пускает своих пользователей, суперадминистратор без схемы по-прежнему входит.
